# 52. No lens classifies a new table's replication data-class and direction (R2), only Product gets asked

At Chain/Organization scale a feature routinely adds a table that must exist at branch and be seen at brand, or be set at brand and obeyed at branch — a fact or a policy. `replication.registry.ts` enforces the FACT-up/POLICY-down pairing by throwing at boot, but nothing in the scoping process asks the question before the code is written, for any entity but Product. A feature ships against a registry it hasn't budgeted for, or ships a correctly-classified table that reaches no listener and silently never leaves its node — and even a correctly wired table can still pile up in a quarantine table nobody has a screen to look at.

## Lens: The registration that either exists or gets carved around

**Question:** For every new table this feature adds that must be visible outside the node that writes it, name its `dataClass` (`FACT` or `POLICY`), its `direction` (`UP` or `DOWN`), and the module and method where `ReplicationRegistry.register()` is called for it — or state that the table never leaves its node and why that is correct at Organization scale (100+ locations).

**Why:** `replication.registry.ts:28-35` rejects any FACT/DOWN or POLICY/UP pairing at registration time, citing R2 in the thrown error. `_canonical-decisions.md` Ruling 8 rules this is never relaxed — an upward flow that isn't a fact "does not have an upward flow, it has a request for a second replication direction." `_conflicts.md` #8 names the failure mode verbatim: hitting the throw under deadline produces "an exception in the registry for this one entity" that is "invisible six months later" and becomes "the thing the next conflict... will cite as precedent." This lens is the general form of file 18's *The propose-up path that never opens*, which only asks whether `Product` carries a `scopeLevel`/`originNodeId` column pre-registry; this one is every new table, at the registry boundary, at registration time, for any module.

**Worked example:** Narrow slice: a Tranche 5 chain-operations feature adds `RegionalPricePlan` (brand sets it, branches must obey it) and ships the service, controller and tests — no replication call. It works in the demo because the demo has one node. Complete capability: the plan states `RegionalPricePlan: { dataClass: 'POLICY', direction: 'DOWN' }`, names `PricingModule.onModuleInit()` as the registration site (matching `ProductReplicationListener.onModuleInit()` at `product-replication.listener.ts:42-48`), and either ships `applyIncoming()` for it or states plainly, like `OrderReplicationListener.apply()` does (`order-replication.listener.ts:40-44`, "this fact is held, not lost"), that the listener throws a named-reason error until a later work order builds it.

**Done test:** The PR's scope-lens section names, per new cross-node-visible table, one `entity` string; `grep -rn "registry.register('<entity>'" apps/api/src/modules` returns exactly one registration whose `dataClass`/`direction` pair is FACT/UP or POLICY/DOWN (the other two combinations fail at boot by construction, so a passing boot is not itself proof — the grep must show the registration exists at all). A table named "brand-visible" or "branch-visible" in the plan with no matching `register()` call fails review.

**Breaks without:** Two failure shapes, both silent until Tranche 3/5 land: (a) the registry throws at boot under deadline and a reviewer, following `_conflicts.md`'s predicted path, carves a one-off exception into `replication.registry.ts` that the next feature cites as precedent, eroding the one mechanical guarantee R2 has; (b) a table is correctly classified but wired to no listener, so — per `00a-ground-topology.md`'s own note that replication is "dormant machinery" with only Product and Order having listeners today — a brand-tier report or screen reads zero rows from every branch with nothing in the diff to explain why, and nobody notices until an area manager asks why their number is zero.

## Lens: The quarantine nobody opens

**Question:** For every table this feature registers with `ReplicationRegistry`, when `apply()` throws or a schema-version mismatch fires, `ReplicationQuarantineService.quarantine()` writes a row — name the controller route and the `@RequirePermission` key a real role holds that lists it (`listOpen()`) and resolves it (`resolve()`), or state which existing screen already covers this entity's quarantine queue.

**Why:** `replication-quarantine.service.ts` implements `quarantine()`, `listOpen()` and `resolve()` today, but no controller in `apps/api/src` calls any of the three (`grep -rn "Quarantine" apps/api/src --include='*.controller.ts'` returns nothing) and no permission key like `replication.quarantine.resolve` exists anywhere the `@RequirePermission` decorator is used. `OrderReplicationListener.apply()` (`order-replication.listener.ts:40-44`) already throws unconditionally for every incoming `Order` fact today, so every chain deployment that reaches Tranche 5's chain-wide order view is already writing rows into a table nothing can read. This is a different failure than the previous lens's registration gap: a table can be correctly classified, correctly wired to `register()`, and still be invisible, because the record-of-failure path was never given a door.

**Worked example:** Narrow slice: `RegionalPricePlan` registers as `POLICY`/`DOWN`, ships `applyIncoming()`, and a schema-version bump three months later starts quarantining every incoming record silently — the feature that shipped the bump never touched the quarantine path because it didn't have to compile. Complete capability: the plan names `ReplicationQuarantineController` (or an existing admin controller) exposing `GET /replication/quarantine` and `POST /replication/quarantine/:id/resolve`, gated by a named permission a real role in `ROLE_PERMISSION_SEED` (or its equivalent seed) actually holds, and a nav entry under an operations or platform-admin section.

**Done test:** `grep -rn "ReplicationQuarantineService" apps/api/src --include='*.controller.ts'` returns at least one match naming the entity's owning module, and a corresponding `@RequirePermission` key on that route resolves to a role grant in the seed file, not only a `Permission` catalogue row.

**Breaks without:** Every schema-version mismatch or `apply()` throw across every registered entity accumulates in `ReplicationQuarantine` with `status: 'OPEN'` forever — nothing pages anyone, nothing lists it, and `resolve()` is dead code. At Organization scale with dozens of nodes syncing continuously, that table becomes the silent record of every sync failure the business has had, readable only by a direct database query, and a brand-tier number built from replicated facts is wrong by exactly the count of rows stuck there with nobody able to say so from the product.

## Not modelled yet

- A registry-adjacent lint (like `check-module-boundaries.mjs`) that fails the build when a Prisma model tagged as chain-visible in a doc comment has no matching `ReplicationRegistry.register()` call — today this is caught only by the registry's runtime throw at boot, or not caught at all if nobody ever calls `register()` for it.
- A quarantine-age alert (e.g. a scheduled check that pages when a row's `status` stays `OPEN` past a threshold) — today `listOpen()` exists with no caller, so nothing surfaces age at all.
