## Where a narrow build goes wrong here

- The thirty existing lenses already occupy the obvious enterprise axes (scope/isolation, reversal, concurrency, bulk, policy versioning, resilience, notifications, integrations, reporting, edition spectrum). New lenses that restate 'name the scope column' or 'name the idempotency key' will duplicate lenses 10, 17 and 28. The genuinely empty ground is the twelve Generate topics that produced nothing: approval chains and delegation, segregation of duties, audit/evidence/legal hold, data privacy and retention, identity/roles/ranks, money integrity, commercial contracts and B2B, localisation and jurisdiction, security/fraud/insider risk, observability and day-two ops, onboarding and documentation, omnichannel surface parity.
- There is no rank, department, cost-centre, approval or delegation model in the 115-model schema. A lens phrased as if these exist will be unanchorable. Lens 10 already rules that a feature needing a department is proposing a fourth axis and must say so in DECISIONS.md - any new lens in that space must respect that ruling rather than contradict it.
- Today's reality is 4 UserRole values and 50 permission keys, not 100+ roles. Lenses must be written as scaling obligations on a codebase that is not there yet, and must say so, in the same honest register CLAUDE.md uses for its unenforced rules ('Three of these are not machine-enforced yet').
- CLAUDE.md is already 873 lines and the Feature scope section is 83 of them. Appending thirty more lenses inline would violate law 6 and law 3 as applied to the rule file itself. The file's own pattern is a short binding summary plus a link to the long form in docs/implementation/ - new lens material likely belongs in a docs/implementation file with a tight pointer from lines 144-226.
- CLAUDE.md L401-402 asserts apps/pos has no global-error.tsx, not-found.tsx or error.tsx; all three exist today. Any edit touching No dead ends must not copy that stale claim forward.
- Every lens in the prior file carries exactly four labelled parts - Question, Why, Worked example, Done test, Breaks without (five). Deviating from that shape across a merged file will read as two systems, which the globalization rules explicitly call the worst failure mode.
- Reachability is three concrete artifacts here: a route folder under apps/web/src/app/(admin)/admin/(app)/, an ADMIN_NAV entry in apps/web/src/components/admin/nav-registry.ts with permissions + module, and a key in both PERMISSION_CATALOG and ROLE_PERMISSION_SEED. A lens about capability visibility that names fewer than those three is not checkable. POS, storefront and the three-page customer dashboard have separate nav files and no registry equivalent - a capability landing only in admin nav is invisible on the till.
