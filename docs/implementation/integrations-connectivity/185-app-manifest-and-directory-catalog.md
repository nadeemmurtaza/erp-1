# 185 — The app, described: listing, versioned manifest, requested scopes, event topics, and the directory every tenant browses

> **Status: proposed, not yet built.** No `AppListing`, `AppVersion` or
> manifest validator exists (grep, `main` at `642b2831`). Everything reused
> is cited to its file. Part of the program introduced in
> [doc 184](./184-app-platform-overview-and-remote-only-decision.md)
> (ADR-073). An app is always a remote service (doc 184 §2): nothing in a
> manifest is ever executed, imported or evaluated by NEWAX. It is data,
> validated by a pure function and rendered on a consent screen.

## 1. Listing, version, manifest — three things, not one

A GitHub App has a stable identity, a mutable description and a set of
requested permissions that can change over time — and an installation
keeps the permissions it was granted until the installer accepts new ones.
The same split holds here, and each piece gets its own home:

- **`AppListing`** — the stable identity. One per app: slug, publisher,
  category, lifecycle status, visibility, and a pointer to the version a new
  installation gets. It changes rarely and never silently changes what an
  existing installation may do.
- **`AppListingTranslation`** — the display text, one row per locale (en,
  ur), per ADR-006 ("customer-facing text is a row, not a column"). Editing
  it needs a review (doc 186 §3) but never a re-consent.
- **`AppVersion`** — one immutable, submitted manifest. Once submitted it is
  never edited; a correction is a new version. The version is what a
  reviewer approves and what an installation's consent names.

```prisma
// apps/platform/prisma/schema/app-directory.prisma — new file, control-plane DB.
// Same "data about the ecosystem, never tenant business data" boundary as
// marketplace.prisma (doc 165/166) — see doc 184 §3.

enum AppCategory {
  ACCOUNTING
  PAYMENTS
  SHIPPING
  MARKETING
  ANALYTICS
  HR_PAYROLL
  COMMERCE_CHANNELS     // marketplaces, social selling
  COMMUNICATION
  COMPLIANCE
  OPERATIONS
}

enum AppListingStatus {
  DRAFT        // publisher is preparing it; never visible to a tenant
  LISTED       // an approved version exists; installable per `visibility`
  UNLISTED     // publisher hid it from browse; existing installations unaffected
  SUSPENDED    // NEWAX's kill switch (doc 191 §3) — every installation suspended
  REMOVED      // terminal: every installation uninstalled (doc 191 §3)
}

enum AppListingVisibility {
  PUBLIC       // every tenant with a directory credential sees it
  INVITE_ONLY  // only tenants named in AppListingInvite — the curated first phase (doc 195)
}

model AppListing {
  id               String               @id @default(cuid())
  publisherId      String
  /// Generated by the platform from the first translation's name at creation
  /// and never changed after — a single writer, so the adoption test is
  /// moot (doc 184 §Scope lenses). A publisher's rename changes the
  /// translation, never the slug an installation already references.
  slug             String               @unique
  category         AppCategory
  status           AppListingStatus     @default(DRAFT)
  visibility       AppListingVisibility @default(INVITE_ONLY)
  /// The version a NEW installation receives. Null until a first version is
  /// APPROVED. Existing installations move per §5, never by this pointer alone.
  currentVersionId String?              @unique
  /// NEWAX's own apps (the curated first catalogue, doc 195) — shown with a
  /// "Built by NEWAX" marker. It is never a review exemption: a first-party
  /// app goes through the identical pipeline (doc 186 §3).
  isFirstParty     Boolean              @default(false)
  /// Validated raster icon (§6) — stored here, never hotlinked from the
  /// publisher's domain, which would tell the publisher which tenants' admins
  /// opened the directory.
  iconPng          Bytes?
  iconSha256       String?
  createdAt        DateTime             @default(now())
  updatedAt        DateTime             @updatedAt

  publisher      AppPublisher            @relation(fields: [publisherId], references: [id])
  translations   AppListingTranslation[]
  versions       AppVersion[]            @relation("ListingVersions")
  currentVersion AppVersion?             @relation("ListingCurrentVersion", fields: [currentVersionId], references: [id])
  invites        AppListingInvite[]
  reports        AppListingReport[]
  statusChanges  AppListingStatusChange[]
  pricePlans     AppPricePlan[]

  @@index([status, visibility, category])
  @@index([publisherId])
}

model AppListingTranslation {
  id          String @id @default(cuid())
  listingId   String
  locale      String   // "en" | "ur" — the same locale keys ProductTranslation uses
  name        String   // ≤ 60 chars
  tagline     String   // ≤ 120 chars — the directory card
  description String   // ≤ 5,000 chars, plain text with line breaks; never HTML (§6)

  listing AppListing @relation(fields: [listingId], references: [id])

  @@unique([listingId, locale])
}

/// INVITE_ONLY visibility — which tenants may see and install the listing.
model AppListingInvite {
  id              String   @id @default(cuid())
  listingId       String
  tenantId        String
  invitedByOpsClientId String
  createdAt       DateTime @default(now())

  listing AppListing     @relation(fields: [listingId], references: [id])
  tenant  PlatformTenant @relation(fields: [tenantId], references: [id])

  @@unique([listingId, tenantId])
}

enum AppVersionReviewStatus {
  SUBMITTED    // automated checks queued
  IN_REVIEW    // automated checks passed; waiting for a human (doc 186 §3)
  APPROVED
  REJECTED     // terminal for this version; the publisher submits a new one
  WITHDRAWN    // publisher pulled it before a decision
}

model AppVersion {
  id                  String                 @id @default(cuid())
  listingId           String
  /// Semver, `MAJOR.MINOR.PATCH`. Monotonic per listing, enforced at submit.
  version             String
  /// The validated manifest (§2) exactly as submitted — immutable. What a
  /// reviewer approves and what a tenant's consent snapshots (doc 187 §2).
  manifest            Json
  /// sha256 over the canonical JSON — the value a tenant's consent row
  /// stores, so "which manifest did they consent to" is one comparison.
  manifestSha256      String
  reviewStatus        AppVersionReviewStatus @default(SUBMITTED)
  /// Computed at submit against the listing's last APPROVED version (§5):
  /// true when an installation must re-consent before moving to this one.
  requiresReconsent   Boolean
  automatedChecks     Json?                  // doc 186 §3 step 1 — every check, pass/fail, with detail
  submittedByCredentialId String            // AppPublisherCredential — provenance (doc 166's registeredByTenantId shape)
  submittedAt         DateTime               @default(now())
  reviewedByOpsClientId String?
  reviewedAt          DateTime?
  rejectionReason     String?

  listing           AppListing  @relation("ListingVersions", fields: [listingId], references: [id])
  currentForListing AppListing? @relation("ListingCurrentVersion")

  @@unique([listingId, version])
  @@index([reviewStatus, submittedAt])
}
```

`AppPublisher`/`AppPublisherCredential` are doc 186's; `AppListingReport`
and `AppListingStatusChange` are docs 186/191's; `AppPricePlan` is doc
192's. They are shown here only as relations.

## 2. The manifest

The manifest is JSON, validated by **one pure function in
`packages/shared/src/app-manifest.ts`**: `validateAppManifest(manifest,
catalogues) → { ok, errors[], normalized }`. Both ends call it:

- the **platform**, when a publisher submits a version (doc 186 §3);
- **every tenant**, before rendering a consent screen (doc 187 §2).

The shared-catalogue convention is `PERMISSION_CATALOG`'s own "one list, both
ends" (`apps/web/src/constants/permissions.ts`'s header). A manifest that
passes on the platform but references a permission key a tenant's older
release does not know fails **on that tenant**. The tenant's directory then
shows "This app needs a newer NEWAX release" instead of a consent screen
that silently drops a scope. This matters at 50,000 tenants on staggered
release rings (doc 171).

```jsonc
{
  "manifestVersion": 1,
  "version": "1.4.0",
  "urls": {
    "homepage":      "https://courier-app.example/",
    "setup":         "https://courier-app.example/newax/setup",       // where the installer's browser lands (doc 187 §3)
    "webhook":       "https://courier-app.example/newax/webhooks",    // omitted ⇔ "events" is empty
    "privacyPolicy": "https://courier-app.example/privacy",           // required
    "terms":         "https://courier-app.example/terms",             // required
    "support":       "mailto:support@courier-app.example"             // required: https or mailto
  },
  "signingKeys": [                                                     // 1–3; the app signs its token requests with the private half (doc 189 §2)
    { "kid": "2026-09", "alg": "ES256", "publicKeyPem": "-----BEGIN PUBLIC KEY-----…" }
  ],
  "permissions": [                                                     // PERMISSION_CATALOG keys — never a parallel scope vocabulary
    { "key": "fulfilment.manage",
      "justification": { "en": "Books shipments and writes tracking numbers back.", "ur": "…" } },
    { "key": "orders.manage",
      "justification": { "en": "Reads the delivery address of orders you ship with us.", "ur": "…" } }
  ],
  "dataScope": "DEPLOYMENT",                                           // the only value v1 accepts (§2.3)
  "events": ["order.placed", "fulfilment.shipment_status_changed"],   // APP_EVENT_TOPICS keys (§3)
  "providers": [                                                       // doc 190 — optional
    { "extensionPoint": "COURIER", "protocolVersion": 1,
      "labels": { "en": "Courier App Express", "ur": "…" },
      "endpoints": { "createShipment": "https://courier-app.example/newax/courier/v1/shipments",
                     "track":          "https://courier-app.example/newax/courier/v1/track",
                     "cancel":         "https://courier-app.example/newax/courier/v1/cancel" } }
  ],
  "pricing": { "planKeys": ["free"] }                                  // AppPricePlan keys on this listing (doc 192)
}
```

### 2.1 Permissions — real catalogue keys, nothing else

Each requested permission is a `PERMISSION_CATALOG` key
(`packages/shared/src/permissions.ts`). The validator refuses, naming the
reason:

- a key not in the catalogue;
- a key in `NON_DELEGATABLE_PERMISSIONS` (`packages/shared/src/api-keys.ts`)
  — the same escalation list personal keys already obey, plus this
  program's additions (doc 189 §3);
- a key in `CHECKER_PERMISSIONS` (doc 189 §3) — an app is never the second
  person of a maker-checker pair;
- a key with no English justification. Reviewers read the justifications
  (doc 186 §3), and the consent screen shows them under each key (doc 187
  §2).

There is **no wildcard and no "all"**. That is doc 34's own "a key scoped to
`*` … is refused at creation" rule, kept.

### 2.2 Why an app asks for admin permission keys and not customer scopes

`CUSTOMER_SCOPE_CATALOG` (doc 163 §4) governs a *customer's* key over their
own rows. An app installed by the business acts for the business, so its
vocabulary is `PERMISSION_CATALOG`. An app acting for an individual
storefront customer — "log in with this shop" for a third-party service —
is a different consent (the customer's, not the admin's) and a different
product. Doc 187 names it out of scope.

### 2.3 Data scope — one value, stated honestly

`"dataScope": "DEPLOYMENT"` means the whole tenant node: every brand and
every branch whose data lives in this database. It is the **only** value v1
accepts. The reason is `ENTERPRISE-SCALE.md`'s own enforcement table: **L2
branch-scoped reads — "nothing … not enforced — gap"**. A consent screen
offering "only branch X" would promise something the routes do not
enforce — and a consent screen is the worst place for a false promise.

The mechanism a narrower scope will use already exists and needs no new
column. An installation's actor is a `User` (doc 189 §1), so a narrower
scope is `AdminScope` rows for that user, read by the same `resolveScope()`
/ `assertCanManageAtScope()` in `core/auth/scope.guard.ts` a human
brand/branch admin is bounded by. When L2 enforcement ships, the validator
accepts `"BRAND"`/`"BRANCH"` and the consent screen offers them. Until
then, a chain that wants one brand's data isolated from an app installs it
on that brand's own node (`RETAIL-ERP.md`: a node has its own database).
That isolation is real today.

## 3. Event topics — an explicit allowlist, never "any domain event"

An app may subscribe only to topics in **`APP_EVENT_TOPICS`**
(`packages/shared/src/app-event-topics.ts`). Each topic names one domain
event from `apps/api/src/core/events/domain-events.ts`, the permission an
installation must hold to receive it, and a pure projection of the fields
the app receives.

Exposing the domain-event catalogue wholesale would be a breach waiting to
happen. `PasswordResetRequestedPayload` and
`EmailVerificationRequestedPayload` carry a **raw token**
(`domain-events.ts:257–267`). `OrderPlacedPayload` carries the customer's
phone and email. `OrderStatusChangedPayload.actorId` is an internal user
id. And an event's shape is an internal contract doc 131 lets change on its
own schedule.

**Every projection is thin: identifiers, a status transition and a
timestamp, never the record.** The app reads the record through the API with
its own credential (doc 189), so **`PermissionsGuard` stays the only thing
that decides what data an app sees**. A webhook payload that carried the
record would be a second authorization decision — a projection function
deciding which columns leave the building — beside the route's own
`@RequirePermission` and column stripping. The two could disagree, which is
the duplicate-authorization defect doc 184 §4 refuses.

| Topic | Domain event (`docs/index/cross/events.md`) | Required permission (guards the detail route the app fetches) | Projected fields |
|---|---|---|---|
| `order.placed` | `order.placed` | `orders.manage` (`GET /admin/orders/:id`) | `orderId`, `orderNumber`, `placedAt` |
| `order.status_changed` | `order.status_changed` | `orders.manage` | `orderId`, `orderNumber`, `fromStatus`, `toStatus` — never `actorId` |
| `order.cancelled` | `order.cancelled` | `orders.manage` | `orderId`, `orderNumber` |
| `payment.succeeded` | `payment.succeeded` | `orders.manage` — payments are read through the order; `GET /admin/payments/awaiting-approval` is gated by `payments.approve`, a key apps are refused (§2.1) | `paymentId`, `orderId`, `provider`, `status` |
| `payment.refunded` | `payment.refunded` | `orders.manage` | `paymentId`, `orderId`, `provider` |
| `catalog.product_published` | `catalog.product_published` | `catalog.manage` (`GET /admin/catalog/products/:id`) | `productId` |
| `catalog.product_changed` | `catalog.product_changed` | `catalog.manage` | `productId` — the event itself is id-only (WO-8.3) |
| `catalog.product_price_changed` | `catalog.product_price_changed` | `catalog.manage` | `productId` |
| `inventory.stock_replenished` | `inventory.stock_replenished` | `inventory.manage` (`GET /admin/inventory`) | `variantId`, `locationId` |
| `inventory.low_stock` | `catalog.product_low_stock` | `inventory.manage` | `productId`, `variantId` |
| `fulfilment.shipment_status_changed` | `fulfilment.shipment_status_changed` | `fulfilment.view` (`GET /admin/fulfilment/shipments/:id`) | `shipmentId`, `orderId`, `fromStatus`, `toStatus` |
| `fulfilment.return_status_changed` | `fulfilment.return_status_changed` | `fulfilment.view` (`GET /admin/fulfilment/returns/:id`) | `returnId`, `orderId`, `fromStatus`, `toStatus` — never `actorId` |
| `purchasing.goods_received` | `purchasing.goods_received` | `purchasing.manage` | `goodsReceiptId`, `purchaseOrderId`, `receivedAt` |
| `purchasing.supplier_bill_raised` | `purchasing.supplier_bill_raised` | `purchasing.manage` (`GET /admin/supplier-bills/:id`) | `billId`, `supplierId`, `issuedAt` |
| `receivables.credit_note_issued` | `receivables.credit_note_issued` | `finance.view` (`GET /admin/credit-notes`) | `creditNoteId`, `orderId`, `issuedAt` |

**Lifecycle topics** are about the installation itself, not tenant data.
Every installation with a webhook URL receives them, whatever it was
granted: `installation.created`, `installation.scopes_changed`,
`installation.suspended`, `installation.reinstated`,
`installation.deleted`. Each carries `installationId`, the granted
permission keys and topics after the change, and `occurredAt`. They come
from this program's own `app_installation.*` domain events (doc 187 §6).

**Deliberately never a topic in v1, with the reason:** `user.*` (tokens,
security notices, account identity); `identity_verification.*` (KYC
outcomes about a person); `payroll.*` and `hr.*` (salary and employment —
a separate, sensitive category needing its own consent review);
`email.reply_received` (message bodies); `wallet.*`, `settlement.*`,
`bank_facility.*` (treasury, with custody questions doc 155 keeps
deliberately narrow); `notification.sent` (metering telemetry, doc 153);
`crm.contact_upserted`/`crm.lead_created` (nothing publishes them —
`events.md` attention list). Adding any of these is a reviewed change to
`APP_EVENT_TOPICS` with its own projection and spec, never a manifest-side
request.

**The envelope** every delivery shares (doc 188 §3):

```jsonc
{ "id": "<OutboxDelivery.id>",           // unique per (installation, event) — the app's idempotency key
  "topic": "order.status_changed",
  "schemaVersion": 1,                    // the topic's own contract, independent of the domain event's (doc 131)
  "occurredAt": "2026-09-28T10:14:03Z",  // the OutboxEvent's createdAt, not the send time
  "installationId": "<AppInstallation.id>",
  "data": { "orderId": "…", "orderNumber": "…", "fromStatus": "PROCESSING", "toStatus": "SHIPPED" } }
```

A topic's `schemaVersion` changes only on a breaking change to its
projection. Then it is published as a new topic key (`order.status_changed.v2`)
beside the old one for a stated window — doc 131's own rule for domain
events, applied one layer out.

## 4. Provider capabilities

`providers[]` declares that the app implements a typed extension point over
a published HTTP protocol (doc 190). v1 supports `COURIER` (protocol v1,
`CourierProvider`) and `PAYMENT` (protocol v1, `PaymentProvider`). The
validator checks:

- the extension point is one doc 190 supports;
- every endpoint in the protocol is present and HTTPS;
- the listing's category matches (`PAYMENT` ⇒ `PAYMENTS`, `COURIER` ⇒
  `SHIPPING`);
- `PAYMENT` additionally forces the licensing attestation review of doc 186
  §3.3.

A `FiscalComplianceProvider` or `VideoConferenceProvider` capability is
**not** accepted: neither interface exists in code. `FiscalComplianceProvider`
is doc 15's design; `VideoConferenceProvider` is doc 205's proposed
`core/video` seam, not yet built. Doc 190 §6 says what makes either bindable
once it exists.

## 5. Versioning — which changes need the installer's consent again

At submit, the platform diffs the new manifest against the listing's last
`APPROVED` version and sets `AppVersion.requiresReconsent`:

| Change | Re-consent? | Review? | Why |
|---|---|---|---|
| A permission key added | **Yes** | Yes | A new capability. |
| A topic added | **Yes** | Yes | New information flows out. |
| A provider capability added | **Yes** | Yes | The app would appear at checkout or in fulfilment. |
| `dataScope` widened | **Yes** | Yes | More rows. |
| A price plan's price raised, or a free app becoming paid | **Yes** (doc 192 §3) | Yes | Money. |
| Any removal (permission, topic, provider) | No — narrowing applies on upgrade | Yes | Less access is never a consent question. |
| A URL changed (setup, webhook, provider endpoint) | No | **Yes, always** | Where data and credentials go is a trust decision (`.claude/rules/security.md`: repointing where a credential is sent is "exfiltration by another name"). |
| Signing key added or rotated | No | Yes, fast-tracked (doc 186 §3) | A compromised key must be replaceable within hours, not a review cycle. |
| Justification/translation text only | No | Yes (translations are policy-checked) | — |

**How installations move.** Every approved version is announced on the
status feed (doc 191 §3). A tenant's poller picks it up:

- a version with `requiresReconsent = false` is applied to every installation
  automatically — narrowed grant, new URLs, new keys — with an
  `AppInstallationConsent` row of kind `AUTO_UPGRADE` recording from→to.
  **A new signing key or a changed URL is applied only once the app's own
  well-known document, on its previously consented domain, confirms it**
  (doc 191 §4.3). The control plane alone can never redirect an app's
  traffic or add a key that mints tokens. Narrowing needs no confirmation,
  because less access is always safe to apply;
- a version with `requiresReconsent = true` leaves each installation on its
  **current grant**. The admin sees "Update available — needs your
  approval" (doc 187 §5), and the app keeps working at its old grant until
  someone accepts.

A publisher must therefore keep serving installations whose grant is older
than its newest version. That is a directory policy obligation (doc 186 §4),
and GitHub imposes the same one.

## 6. The directory a tenant browses

**Platform side** (`apps/platform/src/modules/app-directory/`). Guarded by
the existing `MarketplaceCredentialGuard`
(`apps/platform/src/modules/product-reference/marketplace-credential.guard.ts`)
with no change: "which tenant" is always the presented key, never a
parameter.

| Route | Returns |
|---|---|
| `GET /app-directory/v1/listings?category=&q=&cursor=` | Listings with `status = LISTED` visible to the caller (PUBLIC, or INVITE_ONLY with an `AppListingInvite` for this tenant); keyset-paginated by `(name, id)`, 24 per page; name/tagline in the requested locale |
| `GET /app-directory/v1/listings/:slug` | The listing, its translations, its current version's **manifest**, its price plans, install count (bucketed — "1,000+", never exact, so a competitor's installs are not an oracle) |
| `GET /app-directory/v1/listings/:slug/icon` | `iconPng`, `Cache-Control: public, max-age=86400`, `ETag: iconSha256` |
| `GET /app-directory/v1/listings/:slug/versions/:version` | A specific approved manifest — what an installation on an older version reads to re-render its own consent |

`GET /app-directory/v1/status-feed` is doc 191's. `POST
/app-directory/v1/installations` and reports are doc 187/186's.

**Icons.** `apps/platform` has no storage service. Grep finds no
`StorageService`/`StorageDriver` under `apps/platform/src`, and doc 166's
`GlobalProductReferenceImage.url` is a caller-supplied string despite that
document's "stored once in the platform app's own storage driver". So an
icon is uploaded by the publisher as bytes, checked at submission — PNG or
WebP by magic number, **never SVG** (an SVG can carry script), square, ≤
512×512, ≤ 64 KB — and stored on `AppListing.iconPng`. Stored bytes, not
a hotlinked URL, keep the publisher from learning which tenants browse
their listing.

**Description text is never HTML.** It renders as plain text with line
breaks preserved. A third party's HTML inside the tenant admin's origin
would be the in-process-code problem of doc 184 §2 in its smallest form.

**Tenant side** (`apps/api/src/modules/app-installations/`).
`AppDirectoryClient` is a server-side proxy with the identical shape of
`MarketplaceService` (`apps/api/src/modules/supply-chain/marketplace/marketplace.service.ts`):
`MARKETPLACE_API_URL` + `MARKETPLACE_API_KEY` from
`core/config/env.validation.ts`, the key never reaching the browser. It is
exposed as `GET /admin/apps/directory`, `GET /admin/apps/directory/:slug`
and `GET /admin/apps/directory/:slug/icon`, all
`@RequirePermission('apps.manage')`. Responses are cached per process for 60
seconds, keyed by `(route, locale, cursor)` — directory data is the same for
every admin of this tenant, so there is no auth isolation concern within
one deployment. The icon is cached for 24 hours by its ETag.

**Screens** (`apps/web/src/app/(admin)/admin/(app)/apps/`), one job each:

- `/admin/apps` — **Installed apps** (the overview: name, status, granted
  key count, last delivery status, "Update available"). Doc 187 §7.
- `/admin/apps/directory` — **Browse**: search, category filter, cards
  (icon, name, tagline, "Built by NEWAX" marker, price label). One primary
  action per card: open it.
- `/admin/apps/directory/[slug]` — **The listing**: description, screenshots
  omitted in v1 (§ Out of scope), exactly what the app will ask for (the
  permission list, each with its catalogue label, sensitivity and the
  publisher's justification; the topics; any provider capability),
  publisher, support/privacy/terms links, price. One primary action:
  **Install**, which goes to the consent screen (doc 187 §2).

The nav entry: key `apps`, label "Apps", `href: '/admin/apps'`,
`permissions: ['apps.manage']`, `group: 'settings'`, `module:
'app-installations'` in `apps/web/src/components/admin/nav-registry.ts`,
beside doc 172's `connections` entry.

**Reachability of the directory itself.** It exists only for a deployment
holding a directory credential, i.e. a `PlatformTenant` with an ops-issued
`MarketplacePublisherCredential` whose key is in its `MARKETPLACE_API_KEY`.
Without one, `/admin/apps/directory` shows "This deployment is not
connected to the NEWAX App Directory" with the one action that helps: the
private connections screen (doc 193). It is never an error and never a dead
end. Doc 195 names the enrolment gap: provisioning does not set a tenant's
env today.

## Scope lenses

This document defines data about apps, not access to tenant data; docs 187
and 191 carry the full pass. Lines for what this document uniquely decides:

**Whose rows, and which columns** — directory data is the same for every
tenant that may see a listing; `AppListingInvite` narrows INVITE_ONLY
listings to named tenants. Install counts are bucketed. Nothing about which
tenants installed an app is ever returned to another tenant or to the
publisher, beyond the count bucket.
**Authority and blast radius** — the manifest can ask for at most the
delegatable, non-checker catalogue (§2.1); the worst manifest a publisher
can write is refused by the validator, not a reviewer's attention span.
**The second copy of the write** — `AppVersion @@unique([listingId,
version])`: a retried submission of the same version is refused as a
duplicate, never a second row; `manifestSha256` makes "is this the same
manifest" a comparison.
**The hundred-thousandth row** — listings are thousands, not millions; the
browse query is served by `@@index([status, visibility, category])` and
keyset pagination; the tenant proxy caches 60 s, so 50,000 tenants' admins
browsing produce at most one platform read per page per tenant per minute.
**The version stamp** — an `AppVersion` is immutable; an installation's
consent row stores `manifestSha256` (doc 187 §2), so what was consented to is
reconstructible from stored fields forever.
**The absent collaborator** — no directory credential ⇒ the directory screen
says so and offers doc 193's private connections; the `Installed apps`
screen still works for anything already installed.
**Every other lens** — n/a here: this document writes no tenant data, no
money fact and no stock movement; installation and revocation lenses are
docs 187/191.

## Acceptance

- A manifest requesting `users.manage`, `payments.approve`, `*`, an unknown
  key, or a topic whose required permission it does not request is refused
  by `validateAppManifest()` with a reason naming the item — proven by spec,
  identically on both ends.
- A tenant whose `PERMISSION_CATALOG` lacks a key an approved manifest
  requests sees "needs a newer NEWAX release", never a consent screen
  missing that key.
- An INVITE_ONLY listing is invisible (404, not 403) to a tenant with no
  invite.
- An SVG, or a PNG over 64 KB, is refused at icon upload.
- `diffManifests()` marks every "Yes" row of §5 as `requiresReconsent` and
  none of the "No" rows.

## Out of scope

Screenshots and video on a listing. They are more publisher-supplied media
to validate and store, with nowhere to store them until `apps/platform`
gains a storage driver; named, not stubbed. Ratings and reviews of apps by
tenants — a moderation surface of its own. An app UI embedded in the NEWAX
admin: if it is ever built, it is a sandboxed, separate-origin iframe using
doc 113's short-lived embed-token pattern, never doc 143's federated
JavaScript (doc 184 §2). Customer-consented apps acting for a storefront
customer (§2.2).
