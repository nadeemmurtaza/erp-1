## Domain: Notifications and communications

### Lens: Audience is a capability, not an address

**Question:** For every message this feature sends, name the permission key and the scope (brand, branch/Location, node) that decides who receives it — then state what happens when that query returns zero holders, and when it returns two hundred.

**Why:** Every internal alert in this repo today resolves to one literal string: `inventory.listener.ts:54` sends ProductLowStock to `store.supportEmail`, and `supply-chain-digest.cron.ts` sends all three internal digests to that same inbox. An address is not a person, so no rank owns the alert; there is no scope on it, so a 40-branch chain routes Karachi's variance to whoever reads the Lahore inbox. Writing the audience as `permission + scope` is what forces the four things a hardcoded address hides: a query for users holding a permission within a scope, a defined fallback when nobody holds it (a branch with no assigned manager), a digest or cap when the holder set is large, and an escalation target when the first tier does not act within a stated window. `NotificationMessage` has no field for any of this today — adding one is part of the feature, not a later refactor.

**Worked example:** "Notify someone that stock transfer TR-1042 needs approval." Narrow slice: one email to `store.supportEmail` saying a transfer awaits approval. Complete capability: audience = holders of `inventory.transfer.approve` scoped to the destination Location; zero holders escalates to the brand-level holder of the same permission and records that it escalated; the message carries the branch so a chain manager sees only their own; the approval link re-checks the permission server-side on click, because an emailed link is not authorization; and the identical audience expression drives the in-app inbox badge, so email and UI can never disagree about who owes the action.

**Done test:** Open every `NotificationsService.send()` call site the change adds. Each must pass an audience as a permission key plus a scope id — no literal address, no `store.supportEmail`, no hardcoded role or rank name. For each, the PR states the zero-holder behaviour and names the escalation target. One hardcoded recipient fails the review.

**Breaks without:** With 100+ roles and 100+ ranks, the person who should read an alert is defined by what they may do, not by who they were when the subscriber was written — a hardcoded address is stale the first time an org chart changes. With 40 branches, every module's alerts land in one shared inbox, which becomes a firehose nobody reads, so the alert that mattered is statistically unread. And the same code must serve a 3-role shop and a 120-role corporate: hardcoding the recipient is what makes an edition need a fork, which is exactly what one-main-one-production forbids.

### Lens: Delivery is a fact, not a hope

**Question:** After this ships, which single query answers, for one order number / transfer id / POS shift: was the message sent, to which address on which channel, did the provider accept it, did it bounce, and is that recipient now suppressed? If the honest answer is "read the application log", the feature is not built.

**Why:** `NotificationsService.send()` catches every channel error and calls `logger.error`, by design, so a dead SMTP server cannot block an order. The consequence is that the notification layer has no memory at all: nothing persisted, nothing retried, caller told nothing. Building the real capability forces the parts that are invisible when you only call `send()` — a Delivery row per (template, recipient, channel) with status and provider message id; dispatch through the existing transactional outbox (`EventBusService`/`OutboxDispatcher`) with an idempotency key rather than a bare `Promise.all`, so a replayed OrderPlaced does not mail twice; a provider webhook endpoint that ingests bounces and complaints; a suppression list that hard bounces write and every later send consults; the sending domain recorded per message, because `13-email-service-plan.md` gives each client domain its own SPF/DKIM/DMARC; and an admin view that reads all of it.

**Worked example:** "Email the customer their order confirmation." Narrow slice: call `send({ template: 'order.confirmed' })` and move on. Complete capability: the send is dispatched from the outbox keyed on (event id, template, channel, recipient) so a retried OrderPlaced is not a second email; a Delivery row moves queued → sent → delivered or bounced with the provider id and the sending domain; a hard bounce writes the address to a suppression list and flags the customer record so support sees "we cannot reach this address" instead of the customer simply hearing nothing; the order timeline shows "confirmation emailed 14:02, delivered 14:02" beside the status change; and the returns/dispute path can prove what the customer was told and when.

**Done test:** Take a real id and answer all five questions from the admin UI or one SQL query: sent, address, channel, provider accepted, bounced/suppressed. Then point SMTP at a dead port and re-run the business action: the order/transfer must still complete, a Delivery row must exist with status failed, and the retry must not duplicate an already-successful send. Any "no" fails.

**Breaks without:** At 100+ roles most messages are the only trigger for someone's work — an approval, a variance sign-off, a reorder. A silently failed send is a work item that never starts, and the first symptom is the stockout or the transfer that sat unapproved for a week. Across brands with their own sending domains, an unmeasured bounce rate gets a client's domain throttled or blocked by receiving providers, and the discovery is "our customers stopped getting email" weeks later, with no data to attribute it. And every dispute — "nobody told me the transfer was rejected", "I never got the invoice" — is unanswerable, which at corporate scale is a contractual problem, not a support annoyance.

### Lens: The recipient's daily total

**Question:** Count, for the busiest plausible recipient — a branch manager at a 40-branch chain on a stocktake night — how many messages this feature adds to their day, on which channels, at what hours. Then say which of them may wake that person at 2 a.m., which collapse into a digest, and which they are allowed to switch off.

**Why:** Notification is the one layer where every module's output converges on a single human, and no module can see the total. Nine call sites across orders, payments, inventory, stitching, users, marketing and analytics each reasonably send one message; the recipient receives the sum, and nobody owns the sum. The only control that exists today is `user.marketingEmailOptOut` — one boolean that cannot tell "stop selling to me" from "stop paging me about low stock", so the real preference matrix is everything-or-marketing-off. Forcing the count discovers what is missing: a declared class per template (transactional, operational alert, approval-required, digest, marketing), a per-recipient per-class per-channel preference with a defined default, quiet hours plus a short explicit list of classes permitted to break them, a digest scheduler, and an honest record of which classes a person may not opt out of because the message is their job. The count also exposes localisation: `NotificationRecipient.locale?: 'en' | 'ur'` is a locale literal in a core type, and a digest with no translated row must fall back through the brand's locale config rather than dropping English into an Urdu inbox.

**Worked example:** "Alert on low stock for the new inventory feature." Narrow slice: one email per variant that crosses its reorder point. Complete capability: 40 branches by a few thousand variants makes a stocktake night produce thousands of crossings, so ProductLowStock is class operational-digest — one message per branch per morning listing the variants, never one per variant; it is held during quiet hours because it is not worth a 2 a.m. push, while PaymentAwaitingApproval above a stated value threshold is class approval-required and is allowed to break them; the branch manager may move the digest from email to in-app but may not silence it, because the reorder is their job, and that is written down rather than left to a boolean; the digest renders in the recipient's locale with the brand fallback, and its subject counts items instead of naming one.

**Done test:** Write the number down. The PR states the actual per-day message count this change adds for the busiest recipient, derived from arithmetic over real row counts or a seeded simulation, not a guess — plus a table row per new template: template → class → default channel → digestible? → may break quiet hours? → opt-out allowed?. A send with no table row fails. Any template claiming "may break quiet hours" names who approved that.

**Breaks without:** Alarm fatigue is not a partial failure, it is total: once a manager receives 200 near-identical notifications a night they stop reading all of them, including the payment approval that is holding up revenue — and the system looks like it is working, because everything was "sent". Across three editions the same code must yield three messages a day for a single retail shop and a morning digest for a 40-branch corporate; with no class-and-digest model the SME build is fine and the corporate build is unusable, which produces a per-client fork. And with one global opt-out boolean, the first complaint about marketing volume is "fixed" by flipping a flag that also silences order confirmations and security notices.

## Domain: Integration contracts and external systems

### Lens: The failure path, and who is allowed to walk it

**Question:** When this integration's call fails for the last time — the final retry, the malformed payload, the callback for a record that no longer exists — which durable store does it land in, which screen lists it, which permission opens that screen, which action replays it, and what makes replaying it twice safe?

**Why:** Every integration ships its success path. The failure path gets a retry loop and a counter, and the counter is where the feature quietly ends. A retry budget that expires into a status column nobody can read is not resilience — it is data loss with a log line. Those five artifacts (store with payload, list, permission, replay, idempotency guard) ARE the failure path; a plan naming fewer than five has not built one, it has built a place for failures to go and be forgotten.

**Worked example:** apps/api/src/core/events/outbox.dispatcher.ts retries 8 times with backoff, then writes status: 'FAILED' and stops. Everything a sale fans out into rides that outbox — the accounting posting rule that writes the journal entry for payment.succeeded, the CRM order subscriber, the stitching work order. The only place a FAILED event surfaces anywhere in this codebase is a number: outboxEvent.count({ where: { status: 'FAILED' } }) in core/health/health.controller.ts and again in modules/money/analytics/analytics.service.ts. No screen lists the rows, nothing shows the payload, no @RequirePermission key exists for looking, and there is no replay — so an order whose journal entry failed to post is a count of 1 on a dashboard and an unbalanced ledger nobody can name. The correct shape is already in this repo one directory away: core/replication/replication-quarantine.service.ts stores the failed record with its payload and reason, exposes listOpen(), and makes resolve() a manual audited step. Any change that publishes a new domain event or calls a gateway, courier or bank inherits the obligation to build that shape, not the counter.

**Done test:** For each external call and each domain event the change introduces, the plan names five things: the durable store the final failure lands in WITH the payload (not just an error string), the admin surface that lists it, the @RequirePermission key guarding that surface, the replay or resolve action, and a test that replays the same payload twice and asserts exactly one effect. Four out of five is a fail. Any of the five answered with 'the log', 'the health endpoint count' or 'we alert on it' is a fail.

**Breaks without:** At one retail shop with four staff, a stuck webhook is someone noticing an order looks wrong and phoning the developer. At corporate edition — 100+ roles, several brands, a node per branch — nobody holds the whole picture, and 'who fixes a stuck payment settlement at 2am' has to be a permission somebody was granted, not a psql prompt. Without it every integration failure escalates to an engineer with production database access, which is exactly the standing access the PBAC model exists to avoid handing out; and the failures nobody escalates become a finance reconciliation gap found a quarter later, with the raw payload needed to reconstruct it never stored.

### Lens: Which tier owns the credential

**Question:** For every external endpoint this feature talks to, which axis owns the credential and the account — the deployment, the brand, the node, or the individual Location — and what does the system do on the request where that credential is absent, expired, or belongs to a different branch than the movement being settled?

**Why:** An integration written as a singleton is a correct integration for exactly one edition. A retail shop has one merchant account; an SME has one plus a courier; a chain has a merchant ID per branch, a courier pickup account per city, and a tax registration per brand. Which tier owns it is a schema decision, not a config decision — moving a credential from process.env to a per-Location row afterwards is a migration plus a restatement of everything already settled against the wrong account.

**Worked example:** PaymentsService resolves a provider from the PAYMENT_PROVIDERS env allowlist, and each provider (modules/sales/payments/providers/jazzcash.provider.ts, easypaisa.provider.ts) holds one set of merchant credentials for the whole deployment. That is right at retail and SME edition and wrong the day a chain runs two branches on separate merchant IDs: a Lahore branch's Payment settles against the Karachi merchant account, handleCallback writes status: 'PAID', the payment.succeeded event posts a journal entry against the brand's single bank account, and nothing in the system is detectably wrong — the money is simply in the other branch's account. Contrast core/replication/node-credential.service.ts and the PARENT_URL / PARENT_API_KEY pair, where the credential is per-node by construction and env.validation.ts refuses a half-configured pair. The same question has to be answered out loud for couriers (rate, label and pickup account per city), for tax (the NTN belongs to the brand, not the deployment), and for any bank or ERP endpoint a corporate edition adds.

**Done test:** The plan carries one line per external endpoint in the form: `endpoint — owned by <deployment | brand | node | location> — stored in <env | Setting | table.column> — absent behaviour: <refuse | queue | degrade to X>`, and a test exercises the absent-credential path. Automatic fail: a provider secret read from process.env inside code that runs per branch or per Location, a gateway or courier account held in a module-level constant, or an endpoint whose absent-credential behaviour is unstated.

**Breaks without:** The failure is silent and financial, the worst pair there is. Stock, orders and permissions all stay consistent; only the money lands in the wrong account, and it stays wrong until a reconciliation months later. It is also the hardest thing in this list to retrofit: by the time a chain asks for it there are settled Payment rows, posted JournalEntry rows and closed periods all resting on the assumption of one account, and every one of them has to be restated by hand — across brands, under a permission model where no single role can even see all of them.

### Lens: A fact that already happened is never rejected

**Question:** When this integration receives a message from a system we do not control — a gateway callback, an offline POS shift's sales, a branch node's push, a trading partner's inbound order — what does the code do when the message is authentic but does not fit our current state? If the answer anywhere is 'throw', name the money or the movement that already happened on the other side and is not undone by our 4xx.

**Why:** Validation is correct for a message asking permission and catastrophic for a message reporting a completed event. The card was charged; the till took the cash; the branch shipped the box. Rejecting the message un-charges, un-takes and un-ships nothing — it only deletes our record that it happened. Authenticity failures are refused with no write (an unsigned claim is not a fact). Everything that survives the signature check is a fact: accepted, persisted verbatim, and quarantined if it cannot be applied.

**Worked example:** PaymentsService.handleCallback throws NotFoundException('No payment for reference …') when the reference matches no Payment row for that provider, and writes nothing at all — no row, no audit entry, not even the raw payload it was handed. So the case where a gateway callback matters most (a reference lost to a restore, a payment row moved by a branch split, a sandbox callback pointed at the wrong node) yields a 404 to the gateway, a captured payment at their end, an order still PENDING at ours, and no artifact anywhere proving the callback ever arrived. The unverified-signature refusal immediately above it is correct and must stay. A signed callback for an unknown reference is a fact and belongs in the ReplicationQuarantineService shape: stored with payload and reason, listed, resolved by a human. The same question decides the POS sync — when a shift that ran offline pushes its sales and one line references a variant head office deleted meanwhile, RETAIL-ERP.md R5 already gives the answer: a sale that already happened is never rejected by sync.

**Done test:** For every inbound endpoint the change adds or touches, the plan classifies each message as a request (validate and reject freely) or a report of a completed fact (accept, persist verbatim, quarantine if unapplicable). Every fact-shaped endpoint carries a test that sends a well-formed, authenticated message that cannot be applied — unknown reference, deleted variant, closed period — and asserts a durable row exists afterwards with the payload on it. An endpoint that answers such a message with a 4xx and zero writes is a fail. Signature and authenticity failures are the one sanctioned exception: refused, no write, by design.

**Breaks without:** This is the defect that scales worst. At one shop, the operator who took the cash is standing right there and re-enters it. Across 100+ roles, several brands and a node per branch, the person who can open the gateway dashboard, the person who can see the order, and the person who closes the ledger are three different people with three disjoint permission sets, and none of them holds the evidence the other two need — the 404 threw the only copy away. Every such gap becomes a manual finance investigation conducted without the primary source, and an offline-capable POS multiplies it: a whole shift's sales arriving hours late into a database that has moved on is the normal case there, not the edge case.

## Domain: Reporting, analytics and exports

### Lens: Whose rows?

**Question:** Who is this report computed AS — and do the CSV, the scheduled send and the drill-down each apply the same row filter and column mask the screen applied, or does the permission only decide whether the button is visible?

**Why:** A permission key is a door; a report is a window. In this repo `reports.view` opens all eight exports at once and not one query in `reports.service.ts` references `AdminScope`, `scopeFilterFor()`, `locationId` or a brand, so the narrowest role in the system reads the widest dataset the moment it reaches an export. Aggregates also launder row-level permissions: `inventory.view_cost` gates `export/stock-valuation`, but `export/purchases-by-supplier` computes `SUM(gri.quantity * gri."landedUnitCost")` under plain `reports.view` — the forbidden number, summed. And a scheduled report has no viewer at all: `SupplyChainDigestCron` emails `store.supportEmail` computed as nobody, so "is this recipient allowed to see this" is a question the code never asks.

**Worked example:** A Lahore branch manager with `reports.view` calls `/reports/export/stock`. `stockCsv()` reads `ProductVariant.stock` — the brand-wide rollup — not `VariantLocationStock`, so she downloads every branch's stock, and grepping `apps/api/src/modules/money/reports/` for audit returns nothing, so no row records that she did. Building "a stock report" completely means: a scope predicate from `scopeFilterFor()` on the query; the identical predicate on the export and on any schedule built from it; a named service identity for every scheduled run plus a per-recipient permission re-check at send time (not at subscribe time); sensitive columns dropped rather than blanked when the viewer lacks that column's permission; and exactly one audit row per export naming actor, parameters and row count.

**Done test:** For every report, export and schedule, name (a) the identity it runs as and (b) the exact scope predicate and per-column permission checks. Then call the same endpoint twice — once as an org admin, once as the narrowest role that can reach it (single-branch cashier, single-brand accountant) — and diff row count and column set. Identical output for both is a fail. Zero audit rows written by an export is a fail. A scheduled report with no named identity, or whose recipient list is not permission-checked at send time, is a fail.

**Breaks without:** At 100+ roles across branches and brands, one `reports.view` grant becomes a silent org-wide read of landed cost, margin, customer PII and every rival branch's performance — which makes the entire PBAC layer decorative, because the cheapest route around any row-level denial is an export. The client's only defence is making reporting head-office-only, which deletes the feature for every chain and SME that has branch managers, and leaves nobody able to answer "who exported the customer list the week before they resigned?"

### Lens: Click the number.

**Question:** Take any figure this surface shows: which rows produced it, can the reader reach exactly those rows in one click, do they add back up to it, and when another surface reports the same fact, which one is authoritative and what are the enumerated reasons they differ?

**Why:** This codebase already knows the same fact four ways — orders (`salesByDayCsv`), the general ledger (`JournalEntry`/`JournalLine` via `posting-rules.subscriber.ts`), the till (`PosShift` + `CashMovement`), and stock as a rollup (`ProductVariant.stock`) versus a ledger (`StockMovement`) versus per-location truth (`VariantLocationStock`). A figure with no path to its rows cannot be checked by the person held responsible for it, and two figures with no declared relationship do not stay equal — they drift, and then get argued about instead of used.

**Worked example:** A September sales tile summed from `Order` will not equal revenue on the trial balance: orders cancelled after posting create a `reversalOfId` entry, POS sales synced late land in a different `FiscalPeriod`, and an `InterBranchInvoice` moves value with no sale at all. Building that tile completely means the tile links to the order list pre-filtered to precisely its own rows, that list totals to the tile, and the tile states its basis on its face — "ordered, not posted; Rs 142k awaiting posting" with a link to those entries. For a stock figure it means naming which of the three stock sources it read and linking to the `StockMovement` rows behind any delta.

**Done test:** For every dashboard tile and every export total: click through, sum the rows the drill-down actually shows, compare. Exact match, or the surface prints the named difference and links to it. Then for any two surfaces reporting the same fact, point to the line in code or `docs/implementation/` that declares which is authoritative and enumerates the legitimate reasons for a delta. A tile whose drill-down lands on the unfiltered orders list is a fail. A tile that reconciles only because the accounting pack is installed is a fail — the retail edition ships without it and the tile must still answer.

**Breaks without:** Several corporate projects merged into one system means the same fact arrives from POS, storefront, transfers and manual journals; with no declared authoritative source and no enumerated delta, month two of every corporate deployment is a meeting about why two screens disagree, resolved by a developer with a SQL client rather than by the product. And once drill-down is scope-aware, two people legitimately see different totals for the same tile — a tile that does not state its own scope ("3 of 11 branches") gets read out to a board as the company number.

### Lens: The file outlives the app.

**Question:** Opened a year from now by an auditor with no login, can this exported file alone state as-of when, in which timezone, for which branches and brands, under which filters, in which currency, run by whom — and does re-running it over a closed fiscal period return the same numbers?

**Why:** `CsvExport` is `{ filename, header, rows }`. The timezone is used only to name the file (`stock_2026-09-19.csv`); the date range appears as a `Period` column in one export and nowhere in the others; `FiscalPeriod.status` (OPEN/CLOSED) exists and no report consults it; and `purchasesBySupplierCsv` declares its currency by typing `'Value Received (Rs)'` into a header string — unusable for a two-currency corporate and a rebrand leak besides. A number used for a filing, a bank or a board pack has to be reproducible. A live query is not reproducible, and a file that cannot describe itself is not evidence.

**Worked example:** Finance files September purchases from `export/purchases-by-supplier`. In November a backdated `GoodsReceipt` is posted; the same URL with the same dates now returns a different total, and nothing in either file says which is which. Building that export completely means a provenance block the file carries — generated-at with timezone offset, period start and end, the scope the actor's `AdminScope` applied, every filter echoed back, brand, ISO currency code and minor units as their own columns sourced from `BRAND`, the actor, the row count — plus a declared basis (live and non-authoritative, or a stored run), plus a guarantee that where `FiscalPeriod.status = CLOSED` the same parameters return the same numbers or a restatement note naming the correcting entry. Plus the unglamorous formats accountants actually accept: a UTF-8 BOM so Excel does not mangle names, text-qualified SKUs and phone numbers so leading zeros survive, ISO dates, one row per fact.

**Done test:** Export the same closed-period report twice with a correction posted in between; byte-compare the numeric columns — identical, or a restatement note names the entry. Hand the file to someone with no system access and ask period, scope, currency and who ran it: all four answerable from the file alone or it fails. Open it in Excel with a SKU that has a leading zero and a customer name containing non-ASCII characters: both intact or it fails. Any currency symbol, locale or brand name typed into a header string is a fail — it belongs in a column resolved from `BRAND`.

**Breaks without:** A CSV is the exact moment data leaves every guard the system has; once forwarded, an untitled column of numbers with no period, scope or currency is worthless to an auditor and unsafe for everyone else. Across three editions and multiple brands the same export reaches a shop with one currency and a corporate with several, so a symbol in a header is wrong for half the customers. And with no reproducibility over closed periods, no client can use this system for anything they must file — which caps the product at "shop till" regardless of how good the rest of it is.

## Domain: Multi-entity topology and isolation

### Lens: Name the owner, name the reader it refuses

**Question:** For every row this feature writes, which entity does it name — organization, retail brand, sub-brand, branch node, location, terminal? And for every list it reads, name the specific signed-in user who must get back FEWER rows than a super admin, and the exact rows they must never see.

**Why:** A permission key answers "may you view orders". It never answers "whose orders". At 100+ roles the catalogue grows and every single holder of `orders.view` still hits the same unfiltered `findMany`. Scope is a row-filter question, and this repo answers it in exactly one place today: `apps/api/src/core/auth/scope.guard.ts` exports `scopeFilterFor()`, and `grep -rln "scopeFilterFor" apps/api/src/modules` returns one file (`organization/organization.service.ts`) against 118 `findMany(` calls in module services. `scopeFilterFor()` also only ever emits `{ retailBrandId: { in: [...] } }` — there is no branch-level narrowing at all, so a BRANCH-scoped actor already sees their whole brand's rows. Retrofitting is not a filter change, it is a column that was never written: `Order.locationId` is `String?` and null on every web order; `PosShift`, `StockCount` and `JournalEntry` each need a different answer. Note also which names this repo can actually carry: org / RetailBrand (nested via `parentId`) / Node / Location / PosTerminal. **Department and cost centre do not exist.** A feature that needs one is proposing a fourth axis and must say so in `DECISIONS.md` — not overload `Location`, which is a stock-bearing place and will start appearing in transfer pickers and in-transit buckets the moment it is abused as an org unit.

**Worked example:** "Add a stock count screen." The narrow slice is a form and a variance list. Run the lens: a `StockCount` with no `locationId` is a count nobody can physically perform; with `locationId` but no list filter, the Gulberg count supervisor opens the screen and reads Johar Town's uninvestigated shrinkage before its manager has seen it — a firing offence in a real chain. So the feature is the column, a write path that cannot leave it null, a list filter keyed on the actor's BRANCH grant (which `scopeFilterFor` cannot produce today and must be extended to, not hand-rolled beside), the R19 branch chip naming which branch's counts are on screen, and the brand-tier roll-up its stock controller uses to compare the two branches. Five things, one of which was the original request.

**Done test:** The PR lists every table it creates or alters with the scope column each carries. For every list endpoint it adds, a test exists in which an actor holding the required permission but scoped to brand/branch B receives **zero** rows owned by A — asserting a row count, not a 200. Any table with no scope column carries a written sentence: "this fact is true for the whole deployment because ___." A list endpoint with neither a scope filter nor that sentence fails review. A hand-rolled `where: { locationId: actor.locationId }` inside a service also fails — it goes into `scope.guard.ts` beside `scopeFilterFor()`, or there are two scoping systems by the second call site.

**Breaks without:** The first multi-branch deployment leaks across branches on day one and nobody notices, because every developer tested as the only actor that exists in every deployment today — a super admin with zero `AdminScope` rows, for whom `scopeFilterFor()` deliberately returns `{}`. Then it becomes unfixable in place: add `locationId` to `Order`/`PosShift`/`StockCount` after twelve branches are live and every historic row is either null — invisible forever, since Prisma/Postgres `in` never matches NULL — or backfilled by a guess that quietly reassigns another branch's revenue.

### Lens: The other end, and what nets it out

**Question:** When this feature moves value, a document, stock or a person across an entity boundary, what exists at the other end, who approves at which tier, and what makes the matched pair net to zero at the tier above?

**Why:** A cross-entity flow is never one feature; it is three — the send side, the receive side, and the elimination — and only the send side is ever what gets asked for. R17 states the failure exactly: if brand A transfers to brand B at a transfer price, A books revenue and B books cost, and summing the two P&Ls double-counts because the group sold nothing to anyone outside itself. The columns for the fix already exist — `Account.isIntercompany` and `JournalLine.counterpartyBrandId` (accounting.prisma:40, 197) — which is precisely the danger: a feature that posts a cross-entity journal and leaves `counterpartyBrandId` null has silently opted out of consolidation, and nothing throws. Settlement is likewise not the feature's choice: R12 resolves `transfers.settlement_mode` per source/destination pair (owned→owned inside a brand is `NONE`, brand-to-brand is `INVOICED` by construction), gated by `Organization.allowInterBrandTransfers`, which defaults false. And because R3 forbids distributed transactions, the two ends live in two databases and **will** disagree — that is a normal Tuesday, not an edge case.

**Worked example:** "Let branches request stock from each other." The slice is a request button. The complete capability: (a) the approving tier — same-brand pairs approve at brand under `BrandPolicy.allowInterBranchTransfers`, cross-brand pairs require `Organization.allowInterBrandTransfers` and are `INVOICED` by construction; (b) the receiving side's right to short-receive, and what a 10-of-12 receipt does to the sender's ledger — the in-transit `Location` (R4) is what keeps the missing 2 from being in two places or no place; (c) settlement mode resolved per pair, never per feature, with stock moving at weighted-average cost so margin stays honest; (d) `counterpartyBrandId` on every journal line the flow posts; (e) an unmatched-intercompany exception report, because in real groups that report is how the errors are found. The request button is maybe a tenth of it.

**Done test:** The plan draws the flow as a pair of writes and names which database each lands in. Three questions are answered in writing before code: who approves at which tier, what happens when the two ends disagree (short receipt, rejection, timeout, never-received), and which screen would show the resulting imbalance. If the flow crosses a legal entity, a test asserts that after the flow completes the **group** P&L is unchanged — nothing was sold outside the group — while both brand P&Ls moved. The lens fails if the answer to "what nets this out" is "the sum is correct because both sides are correct."

**Breaks without:** The organization's reported revenue is a lie that compounds: six brands moving stock internally inflate group revenue in every board pack, every bank covenant calculation and every valuation, and the error surfaces when an auditor asks, not when the code runs. The unmatched half is worse — with no reconciliation the saga's failure mode is permanent stock loss: brand A has dispatched, brand B never received, the in-transit bucket holds units nobody is accountable for, and the only person who can tell you is a warehouse man counting cartons.

### Lens: The edition above and the day it appears

**Question:** What is this feature in a Solo deployment where there is one implicit brand and zero `Organization` rows — and what happens to every row it already wrote on the day a second entity appears above it?

**Why:** Three sale scales are three configurations of one build (R14), and `organization` is off by default in every deployment today (organization.prisma's own header says so). So every feature here is written and tested in the edition where the topology is invisible, then ships into the edition where the topology decides money. Two traps are already sitting in this schema. First, nullable scope columns: `JournalLine.retailBrandId` is `String?`, and `scopeFilterFor()` narrows with `retailBrandId: { in: [...] }` — which never matches NULL — so every row written before the org tier was switched on becomes invisible to every brand- and branch-scoped admin the instant it is switched on, with no error. Second, "absence means everything" defaults: `AdminScope`'s own composite unique is documented in-schema as no protection at ORG and BRAND level because a NULL in any column exempts the row from comparison. The same shape of bug in a `where` clause instead of a unique index is a data leak rather than a duplicate grant.

**Worked example:** "Add a P&L report." In Solo it is one query with no scope argument and it looks finished; it even passes review. Switch on a two-brand org and four things are missing at once: the card must take a scope argument, because R19 is one dashboard rendered at three scopes and not three dashboards; the chip row derives from `AdminScope`, never a hardcoded brand list; R17's eliminations apply between separate brands but explicitly **not** between sub-brands, which are divisions of one legal entity sharing one database; and every `JournalLine` written before `RetailBrand` rows existed carries `retailBrandId = null`, so the brand P&Ls sum to strictly less than the group P&L by exactly the amount of history. The complete feature therefore includes the written decision that null means this deployment's own brand, executed as a forward-only migration, rather than discovered later as a variance nobody can source.

**Done test:** The plan states the feature's behaviour in Solo, Chain and Organization editions in one sentence each. "Not applicable" is allowed, but must name the gate that hides it (the `MODULES` allowlist entry or `NODE_ROLE`) and the app must still boot with that module absent — House Rule "every pack must be survivably absent". Every scope column the feature adds is either NOT NULL with a default naming this deployment's own entity, or the PR writes down what null means AND names the query that will silently skip those rows. A nullable scope column with no written meaning fails the lens. Fails also if any screen the feature adds renders a brand picker, an org drill-down or a chip row when there is one entity — that is Law 3 inverted, the smallest customer being shown the biggest product.

**Breaks without:** Two failures at opposite ends of the customer range, from one omission. The retail shop gets an empty brand selector and a drill-down over a single row, so the cheapest edition is the one that looks most bloated. The corporate group gets silent under-reporting: no exception, no log line, just brand P&Ls that don't sum to the group and history that can no longer be attributed, because by the time the gap is noticed nobody can say which brand a 2026 journal line belonged to. Both are found by a customer, not by `pnpm test`, because a single-entity test fixture cannot fail either one.

## Domain: Scale-tier spectrum: retail to corporate

### Lens: Three silhouettes

**Question:** Before writing a file: draw this capability three times — as the one-shop retailer sees it, as the 40-branch chain sees it, as the group-of-brands sees it. Which tier concepts (Location, branch, brand, node, scope, approval threshold, GL account) does it acquire at each step, and which of those must exist in the schema from its FIRST migration while never rendering on the Solo screen?

**Why:** R14 says the three sale scales are three configurations of one build. The only way that survives contact with a second client is to know the Chain and Organization shapes before the Solo one is written, because the tier-bearing column has to be in the first migration — added later it is a second migration that leaves every existing row NULL, and a second screen to read it. The precedent already in this repo is B6's single `MAIN` Location: every deployment has had one for years and no user has ever seen it. Every new capability needs its own `MAIN` — present, defaulted, unrendered. The difference between editions must be rows, scope and module flags, never a branch in code: `if (edition === 'SOLO')` is the same defect the three-axes rule already bans as `if (sector === …)`.

**Worked example:** "Add a stock adjustment screen." Solo silhouette: quantity, reason, save — `locationId` resolves to `MAIN` and is never rendered, no approval step exists. Chain silhouette: the same route, same component, same permission family, plus a Location column that appears because the signed-in user's scope spans more than one Location, plus an approval threshold read from a brand policy row (policy replicates down, R2). Organization silhouette: an adjustment over threshold posts a shrinkage journal to a brand-owned account and lands on the org exception report. One route, one component; the deltas are a `Location` row, a policy row and the `accounting` flag in `MODULES`. Drawn this way, the first migration carries `locationId` and the approval columns on day one, and the Chain client is an env change.

**Done test:** Boot `NODE_ROLE=STANDALONE` with the Solo `MODULES` set and exercise the new route and its endpoints: the strings brand, branch, node, scope, sync and organization appear in zero rendered pages, zero API response bodies and zero `navFor()` entries. Then boot `NODE_ROLE=BRAND` with `organization`/`transfers` on: the same route shows the tier controls with NO file added — the diff between the two runs is env plus seeded rows only. `grep -rn "=== 'SOLO'\|nodeRole ===\|EDITION" <feature dir>` returns 0 outside `core/settings/document-number.ts`-style shared helpers. The feature's first migration contains its tier-bearing columns.

**Breaks without:** You ship the Solo screen; the chain client arrives; someone adds `branchId` in a second migration and a `StockAdjustmentsChainPage`. Three things break at once. (1) The R14 upgrade demo fails — Solo rows have NULL branch, so the brand dashboard total no longer equals the Solo total and the upsell needs a conversion project. (2) The approval rule now exists in two components and they disagree within a quarter. (3) The second page carries a new permission key that appears in none of the existing role grants, so the chain's 40 branch managers get 403 on the only screen their job consists of — and at 100+ roles nobody can enumerate who lost access, because the answer is a join across role assignments and per-user overrides that no screen renders.

### Lens: The absent collaborator

**Question:** List every module this capability reads from, writes to, or emits toward that is OFF by default in this repo — `organization`, `accounting`, `pos`, `transfers`, `identity-verification` all are. For each one: when it is absent, what fact is still recorded, what is silently not recorded, and what does the user see instead of the control that depends on it?

**Why:** `FEATURE_MODULES` has 22 togglable entries; a deployment is any subset. "Every pack must be survivably absent" is already a law, but it is only ever tested at boot — and the failure this lens catches is not a crash, it is a capability that boots clean and quietly records nothing. `isModuleEnabled()` in `apps/web/src/utils/module-gate.ts` deliberately fails OPEN when `GET /meta` has not resolved, so an ungated control does not hide itself; it renders and then 404s. Asking the absence question up front turns each optional collaborator into either a domain-event subscriber (absent = no subscriber = no journal, which is correct and invisible) or a gated control (absent = the tab does not exist), and forces you to say which before the code exists.

**Worked example:** The owner's returns portal. A return touches: refund (`payments`), restock via `InventoryService.move()` naming a Location (`inventory`), credit-note journal (`accounting`, OFF), return to a different branch (`transfers`, OFF), in-store return of a web order (`pos`, OFF), ID check on a high-value cash refund (`identity-verification`, OFF). Built on a dev box with everything on, it ships a portal that on a Solo shop refunds money and posts no journal — correct, because nothing subscribed — but also renders an empty "Credit note" panel with no explanation and a "Return to another branch" option that 404s. Answered up front: the refund itself depends on no optional module; the credit note is a subscriber to `return.completed`, absent means no journal and the tab is not registered; return-to-branch is module-gated on `transfers`; the ID check is an extension-point hook, not a call.

**Done test:** The capability's e2e test runs twice: once with the maximal `MODULES`, once with the minimal set (the three `alwaysOn` entries plus only what the feature genuinely requires). Both pass, and the assertions differ only in what is ABSENT — never in what errored, 500'd, or rendered an unexplained empty panel. Under the minimal set, cross `navFor()` output against the route table and assert zero nav entries resolve to a 404 (asserted against the table, not by clicking). `grep` the capability for a direct import of any optional module's service: must be 0 — it reaches them through domain events or a `core/extension-points/*.registry.ts` hook, and `pnpm lint`'s boundary check agrees.

**Breaks without:** 22 togglable modules is millions of possible deployment shapes and every developer tests exactly one. The resulting bug class never throws: the retail shop's refunds never reach a ledger nobody told them they did not have; the SME that switches `accounting` on in month four gets a GL that starts mid-story with no opening balance and a trial balance that cannot be reconciled backwards; the chain discovers "Return to another branch" 404s only with a customer at the counter. Each is a support call whose root cause is one flag in an env var, which is the least reproducible defect there is — it is invisible in the environment where it was written, and the 100+ roles make it worse, because the first report arrives as "the returns screen is broken for warehouse supervisors" rather than "the module is off".

### Lens: The adoption test

**Question:** This capability writes rows and generates human-readable values. If this customer becomes branch #1 of a brand master tomorrow, which of those rows must the adopting tier rewrite — and which generated number, code or slug could two nodes produce independently, offline, and collide on at merge?

**Why:** R14's commercial claim is that Solo → Chain → Organization adds nodes ABOVE an existing one with every primary key unchanged. cuids make that true for ids (R6). It is not true for the ~20 `@unique` constraints on human-supplied and generated values that R6 enumerates — `Order.number`, `PurchaseOrder.number`, `StockCount.countNumber`, `Product.slug`, `ProductVariant.sku`, `Location.code`, `Payment.reference`. Any counter, code or slug a new capability invents joins that list, and the moment to make it node-safe is the first migration, not the merge — because by the merge the colliding rows already exist in production at every customer. The same question flushes out singleton assumptions ("one chart of accounts", "one fiscal calendar", "one price list", "one cash drawer") that are true at retail scale and false at corporate scale.

**Worked example:** `documentPrefix()` in `apps/api/src/core/settings/document-prefix.ts` now issues `TRF`, `IBI`, `INV` and `JE`. A transfer numbered `TRF-2026-0007` from a single Postgres counter row is unreachable from an offline branch box — and R5 says a sale that already happened is never rejected by sync — and is guaranteed to collide when two branches both allocate `0007` offline. The answer already exists and must be used: `documentNumber()` in `apps/api/src/core/settings/document-number.ts` folds `nodeId` into the sequence and collapses to the identical historical `PREFIX-YEAR-SEQ` under `NODE_ROLE=STANDALONE`, so the Solo user never learns the node code exists — the `MAIN` Location trick applied to numbering. The same pass converts any new branch-scoped `@unique` into `@@unique([originNodeId, value])` on day one, and writes the justification next to any surviving "there is only one of these".

**Done test:** Run the R14 upgrade demo against this feature's own data: take a Solo database that has used it, stand a brand master above it, adopt it as branch #1 — assert every primary key unchanged and the brand-tier total for this feature equal to the Solo total exactly. Then the collision test: two nodes generate the feature's number or code offline for the same year, both succeed locally, and the merge completes without a constraint error (a de-duplication decision is an acceptable outcome; a 500 is not). Static checks in the new code, all expected to be zero or justified inline: `autoincrement()`, a bare `@unique` on a generated string, a counter upsert that assumes one database, and any number-formatting string literal that bypasses `documentNumber()`/`documentNumberPrefix()`.

**Breaks without:** The single strongest commercial argument this product has — grow from one shop to a chain and keep your history — becomes a conversion project with a de-duplication spreadsheet, and the retail customer is told their invoice numbers cannot come with them. At the corporate tier it is worse than an inconvenience: two brands in one group each carrying `INV-2026-0001` means the consolidated ledger holds two rows claiming to be the same document, and R17's intercompany elimination cannot match pairs it cannot tell apart, so the group's consolidated P&L is wrong in a way the trial balance still reports as zero. None of it is discoverable before the merge, which is the first day it matters and the last day it is cheap to fix.

## Domain: Bulk operations, import and export

### Lens: The weaker writer

**Question:** Does each row of this bulk run get the same guarantee as the same change made one at a time through the UI — same writer, same transaction, same domain events, same journal lines, same replication rows — and where it deliberately gets a weaker one, does the run's own per-row output name every row that landed in that weaker state?

**Why:** A bulk path is written as "just load the data" and reaches for the cheapest write available, because 5,000 rows in one transaction is a real problem. That trade is often the right one. What is never right is making it invisibly: the operator reads `created` and believes the record is complete, while the code knows the second half of that row was best-effort. The row-outcome vocabulary is the thing this lens forces you to design, and it has to be designed before the loop is written, not bolted on after someone finds a product with no stock.

**Worked example:** `apps/api/src/modules/merchandising/catalog/product-import.service.ts` writes stock through `StockIntakeRegistry.recordIntake()`, and that registry's own doc comment states why: it runs one row at a time outside any transaction, unlike `product-admin.service.ts`'s `create()`/`syncVariants()`, which write stock inside the same Prisma transaction as the variant. It also no-ops entirely when `inventory` is absent from `MODULES`. So on a deployment without that module — or whenever the intake call fails after the product row has already committed — the import creates the product, skips the opening stock, and reports `action: 'created'`. `ImportRowResult` offers exactly three actions: `created`, `updated`, `skipped`. There is no value meaning "product created, opening stock not applied", so the run cannot tell the operator which rows to repair, and the obvious repair (re-upload the file) replays the variant write too.

**Done test:** List every side effect the single-record path produces for this entity: transaction boundary, domain events into the outbox, journal lines from `posting-rules.subscriber.ts`, `AuditService` rows, `ReplicationLogService` rows. For each one, the bulk path either produces it, or the row-result type carries a distinct outcome value saying it did not — and a test asserts that value actually appears when the effect is unavailable (run the importer with no stock-intake handler registered and assert the row is not reported as a clean `created`). A run that performs two writes per row while its result type can only say created/updated/skipped fails this test.

**Breaks without:** At one shop somebody notices a zero and types the stock in. At chain scale the half-applied row is the one that replicates: the branch node receives a product with no movement explaining its stock, `posting-rules.subscriber.ts` posts no opening-inventory journal so the trial balance is short by exactly the un-applied rows, and the analytics pack's `VariantSalesStat` cache is computed on top of the gap. Months later the only way to find which rows were half-written is to diff the original CSV against the inventory ledger, because the import's own record says all 5,000 succeeded. The corporate edition is where this bites hardest: it is the one with replication, accounting subscribers and precomputed caches downstream of the same loop.

### Lens: Row 4,312's authority

**Question:** Which permission, which `AdminScope` grant and which `Location` does each individual row require — the row, not the endpoint — and what does the run do with the rows the uploader is not allowed to touch?

**Why:** A bulk endpoint gets one `@RequirePermission` and a loop, which collapses N authority decisions into one and quietly promotes the route's permission into the permission for every row in the file. This repo already owns the per-row apparatus — `assertCanManage()` for the `_own`/`_all` pairs, `assertCanManageAtScope()` and `scopeFilterFor()` in `apps/api/src/core/auth/scope.guard.ts` for brand/branch grants. The bulk path is exactly where it gets forgotten, because the loop reads like data loading rather than like access control, and because the reviewer is looking at parsing code.

**Worked example:** A manager whose `AdminScope` reaches only the branch they run uploads a 5,000-row stock file. Rows 4,201 onward are another branch's SKUs, pasted in from a head-office sheet. `@RequirePermission('inventory.adjust')` passes once at the controller, the loop calls `recordIntake()` with `stockIntake.defaultLocationId()` for every row, and a branch this person has no grant over has had its stock moved under their actor id. The same shape recurs everywhere bulk lands: a bulk role assignment where the uploader may grant `stitching.jobs.manage_own` but not `manage_all`; a bulk price edit whose rows span two brands; a journal import whose rows fall in a period the uploader may not post into; a customer import whose rows carry identity-document fields the uploader's role may not read back.

**Done test:** A test in which the actor holds the route permission but a deliberately narrow scope, fed a file mixing in-scope and out-of-scope rows, asserts three things: the in-scope rows committed; the out-of-scope rows appear in the result with a reason naming the missing permission or scope; a re-read shows the out-of-scope records byte-identical to before. "Out-of-scope rows silently skipped" is a failure, not a pass — an uploader who is not told which rows were refused will assume the whole file applied.

**Breaks without:** With a dozen roles someone spots the wrong branch's numbers and walks over. With 100+ roles, 100+ ranks and scope grants that change month to month, the audit trail says "bulk adjust, actor X, 5,000 rows" and nobody can reconstruct whether X was entitled to row 4,312 — answering that means replaying X's `AdminScope` grants as they stood at upload time, which a summary row does not record. Worse, the first bulk endpoint sets the pattern every later one copies, so the hole is widest in the edition sold on access control, the only edition with enough roles for scope to mean anything at all.

### Lens: The 14:02 undo

**Question:** It is 14:02, the 09:00 run was wrong: name the rows it touched, their values before it ran, which of its effects cannot be taken back and what the operator does for those instead — then say exactly what happens when they fix the file and upload it again.

**Why:** Bulk features ship with a start button, no stop, no reverse, and no memory of which records they touched. Asking the undo question before building is what turns a run into an entity — an id, a requester, the input file, a per-row outcome, a before-image — instead of a POST that returns counts. Asked afterwards, the only answer available is a hand-written SQL script against production, which the database protocol in this repo forbids outright.

**Worked example:** `product-import.service.ts` records exactly one audit row today: `product.imported`, carrying `{total, created, updated, skipped}`. After a 5,000-row run that overwrote live prices from a stale column, nothing in the system can answer "which 812 products changed, and what was each price before" — the summary counted the rows, it never named them. Several of its effects are already outside the reach of a delete: stock went through `recordIntake()` as movements, and a movement is a fact, so the reverse is a compensating movement; anything the outbox published has reached the branch nodes; an order back-load that fired transactional email has reached customers.

**Done test:** A test imports a file, mutates real records, then calls the documented reversal and asserts the touched rows hold their prior values and that compensating effects were emitted — a reversing stock movement, a reversing journal entry — not that the original rows were deleted. Alongside it, the plan lists each irreversible effect with the operator's recourse; that list may be empty only if the run publishes no domain event, sends no message and posts no journal line, and that claim is checkable by grep. Second half, same test file: run the identical input twice and assert row counts are unchanged — no second `Product` for the same SKU, no second `Party` for the same customer, no second opening journal entry.

**Breaks without:** With no undo, the operator does the obvious thing at 14:05: corrects the spreadsheet and uploads it again. At one shop the duplicates get deleted by hand that afternoon. At chain scale they have already been appended by `ReplicationLogService` and shipped to every branch node, referenced by orders placed in between, and aggregated into an accounting period that has since closed — so the repair is no longer a delete, it is a cross-node merge, and there is no merge tool because nobody planned for the file being run twice. Onboarding migrations from a legacy system are always run more than once; the first run is never the one that is kept.

## Domain: Configurable policy and rules

### Lens: The version stamp

**Question:** When someone edits this rule next quarter, what happens to every record already created under the old one — and can anyone still explain the number on it?

**Why:** Every business rule here is read live at the moment of computation and recorded nowhere. `SettingsService.get()` (apps/api/src/core/settings/settings.service.ts) returns whatever the `Setting` row says now, behind a 30-second in-memory cache, and the `Setting` model (apps/api/prisma/schema/core.prisma:153) is key, value, description, updatedAt — no version, no effective date, no history. `TaxRate` is the only rule in the entire schema carrying `effectiveAt`/`endedAt`. So editing a rule is a silent retroactive rewrite of the meaning of every past record. Orders snapshot the outputs (`shippingFee`, `codFee`, `taxAmount` are stored columns on orders.prisma) but never the rule version that produced them, so a figure can be read back and never justified.

**Worked example:** Asked for "configurable shipping zones per branch." The narrow slice is a zones editor that writes `shipping.zones`. The complete capability: `shipping.zones` becomes a versioned policy row with `effectiveFrom`/`effectiveTo`; `resolveShippingZone()` takes an `asOf` instead of always meaning now; the resolved version id is stamped on the Order and the PosReceipt at placement; the refund path, the returns portal and the credit note re-read the stamped version rather than today's value; the editor shows version history with actor and diff. The same treatment is then owed to `checkout.cod_fee`, `tax.pricing_mode` and `purchasing.over_receipt_tolerance` — every rule whose output is already frozen into a document.

**Done test:** Take a record the rule touched — an Order, PosReceipt, StockTransfer or JournalEntry — created before the rule's most recent edit. Recompute the disputed figure using only that record's own stored fields plus the policy version it names. If the recomputation needs the current `Setting` row, or the record names no version, fail. Then change the rule and re-open that pre-change record's detail page and its refund path: if either number moves, fail.

**Breaks without:** One shop with one rule-setter remembers. At 40 branch nodes and 100+ roles, a COD fee edited at 14:00 makes every receipt printed that afternoon unexplainable: two POS terminals inside the same shift price an identical basket differently within the 30-second cache window, the branch cannot tell the customer why, and the day will not reconcile. A refund six weeks later on an order placed under `tax.pricing_mode: 'INCLUSIVE'` recomputes as EXCLUSIVE, so the refund's journal entry does not balance against the sale's. The auditor's question — why 17% and not 18% — has no answer stored anywhere in the database.

### Lens: Authority and blast radius

**Question:** Of the 100+ roles, exactly which may change this rule, at which of the three scopes (org / brand / branch), does the change need a second signature, and what is the worst value one of them can set before anything notices?

**Why:** A rule anyone with "settings" access can edit is not configurable, it is an unguarded global. Today every business rule in the system — `checkout.cod_fee`, `checkout.min_order_value`, `tax.pricing_mode`, `checkout.allow_backorder`, `marketing.automation_enabled`, `purchasing.over_receipt_tolerance` — sits in one flat global `Setting` table behind exactly one permission string, `settings.manage` (apps/api/src/modules/system/settings/settings-admin.controller.ts), with no scope, no declared bounds, and no record of who changed what to what. `AdminScope` already models ORG/BRAND/BRANCH and `BrandPolicy` already proves a switch can be per-brand — nothing connects a rule to either, so a branch supervisor editing their own fee edits every brand's.

**Worked example:** Asked for "let branches set their own reorder points." Complete: the rule declares its scope level, and the resolver walks BRANCH override → BRAND default → ORG default rather than reading one global key; it is gated by its own capability, `@RequirePermission('inventory.reorder_policy.write')`, not by `settings.manage`; its writable range ships with the rule so a reorder point of 0 or 100000 is rejected by the API, not merely by the form; a change to any rule declared money-moving — `checkout.cod_fee`, `purchasing.over_receipt_tolerance`, `org.allow_inter_brand_transfers` — is written as a proposal that a second holder of an approval permission must activate; and activation writes an `AuditService` row carrying old value, new value, scope, actor and reason. A single-shop deployment sets the approval requirement itself to none, so the shopkeeper approves nothing — one engine, one configuration, not a second code path.

**Done test:** Name the permission string gating this rule and show it differs from the string gating an unrelated rule. Then answer from code: where does a branch-level value override a brand-level one, what value range is rejected server-side, and which line writes the audit row. Missing any of the four — distinct permission, scope chain, bounds, audit — and it is a shared mutable global, not a policy. Finally, a test must attempt the write as a user holding BRANCH scope on branch A against branch B's value and assert 403.

**Breaks without:** At 100+ roles and 100+ ranks, "who can edit settings" stops being a meaningful sentence; the only real question is who can edit *this* rule, and one `settings.manage` string answers "everyone who can edit any rule, everywhere, for every brand." A cashier promoted a rank inherits the grant that sets `checkout.min_order_value` organization-wide, and with no audit row the first symptom is a week of under-priced orders nobody can attribute to a person or a time. At corporate tier, a change to a rule that drives journal entries, made with no second signature and no recorded reason, is a finding in the client's own external audit — not a bug report we get to triage.

### Lens: Dry run before live

**Question:** Before this rule is switched on, can someone replay it over last month's real records and read the diff — with nothing written?

**Why:** A rule observable only by activating it in production is a live experiment on customers. Simulation is not a feature bolted on later; it is a constraint on *where* the rule is evaluated, and it is free to honour before the first line and expensive after. If the decision lives inline in the code that writes — `cart.service.ts` computing a total as it persists, `posting-rules.subscriber.ts` picking an `ACCOUNT_CODE` as it posts the entry — there is no seam to call it a second time, and adding one means rewriting the write path of a module that is already load-bearing.

**Worked example:** Asked for "a discount rules engine." Complete: outcome selection is a pure `evaluate(rule, context) -> outcome` with no Prisma write and no event publish inside it; the checkout path is one caller that persists the outcome; a second, read-only caller replays a draft rule over the last 30 days of real Orders and PosReceipts and renders the diff — orders affected, revenue delta, the ten largest movers — on the rule's own page, with Activate disabled until it has been run. The same seam pays for itself immediately elsewhere: a proposed `purchasing.over_receipt_tolerance` replayed over last quarter's GoodsReceipts states how many receipts it would newly reject, and a changed `inventory.demand_surge_horizon_days` states how many variants tomorrow's digest would alert on — before 400 emails leave.

**Done test:** Open the function that decides the rule's outcome. It must take its inputs as arguments and return the outcome; grep its body for `prisma.` writes and for `publish(` — any hit is a fail. Then check for a second caller that runs it over historical rows without persisting. If the only caller is the write path, fail. A reviewer settles this from one file; there is no partial credit for "a preview can be added later," because the point of the lens is that it cannot.

**Breaks without:** Three staff in one shop activate a bad discount and refund the four customers it hit. A corporate client running the same code across 40 branch nodes activates it at 09:00 and learns at 17:00 from 6,000 receipts already printed and replicated up to the brand tier — where R5 guarantees a sale that already happened is never rejected, so the wrong prices are now facts the system will not undo. And because evaluation lived inside the write path, "what would it have done" is unanswerable even in hindsight; the only remaining instrument is a reversal batch and a letter to the client.

## Domain: Resilience, degradation and offline operation

### Lens: Four hours down, the counter stays open

**Question:** This feature is unavailable for four hours in the middle of trading. Name every actor who was mid-task, what they actually do instead for those four hours, and which surface, permission key and reconciliation job we must build so the work they did by hand gets back into the system — with who did it, when, and against which branch.

**Why:** The narrow slice ships the happy path and files the outage under operations. It is not an operations problem: staff will keep trading on paper, a phone call or a second till, and every one of those facts is created outside the system. Each needs a way back in — a backfill surface, a capability that guards it, an exception queue for the ones that do not match, and a reconciliation proving the fact was not also captured automatically when the service returned. Those are four build items the feature request never mentioned, and asking this question before implementation is the only thing that surfaces them. Skipped, the backfill is written six months later as an emergency SQL script run by a developer, with no actor, no timestamp and no audit row.

**Worked example:** Owner asks for 'stock transfers between branches'. Narrow slice: TransfersService.dispatch() and receive(), both requiring the parent node reachable. Run the lens: the truck leaves Branch A at 09:40, the branch box's uplink dies at 09:45, the goods arrive at Branch B at 14:00. The stock physically left A and physically arrived at B whether or not the API agreed. So dispatch must write into the transfer's own IN_TRANSIT Location locally; Branch B's receiving clerk must be able to receive against the paper docket under a capability created for exactly that (transfers.receive_without_dispatch), not under a blanket inventory grant; a receipt whose dispatch has still not arrived belongs on the branch exception queue rather than throwing; and on reconnect ReplicationSyncAgent matches the two halves by transfer id so the intercompany journal posts once, not twice. Four surfaces and one permission key, all of them part of 'stock transfers', none of them later work.

**Done test:** The plan contains one row per actor with six filled cells: actor, what they do during the outage, the artifact that produces (paper docket, second till, phoned approval), the surface that ingests it afterwards, the permission key guarding that surface, and the reconciliation that proves no fact was counted twice. Any empty cell fails. 'They wait' fails unless the plan states the revenue or safety cost of waiting and the owner accepted it in writing.

**Breaks without:** At 100+ roles the degraded path is a permissions question, not a technical one. Unasked, the backfill screen ends up guarded by nothing — any cashier can key in yesterday's sales — or by an admin-locked key only, which in a 40-branch chain makes one super admin, asleep in another timezone, the single point of failure for every branch's manual recovery. A three-person retail shop survives that; the corporate edition with a four-step approval chain deadlocks at 02:00, and the SME in between discovers that its continuity plan is a WhatsApp message to the owner.

### Lens: Request or record — classify every write

**Question:** For each write this feature performs, is it a request the system is allowed to refuse, or a record of something that already happened in the physical world and therefore can never be refused? For every record, name the unconditional write path, the variance artifact a would-be refusal produces instead, the queue it lands in, who may clear it, and how the books stay balanced.

**Why:** Validation gets written once, from the viewpoint of the surface in front of the author — usually the web admin — and is then reused by the till, the warehouse scanner, the supplier portal and the replication apply path, where 'refuse' means destroying a fact that already occurred. Asking the question per write, before implementation, produces five concrete artifacts every time: a separately named unconditional entry point (never a boolean on the guarded one, so every unguarded call site stays greppable), a variance entity, the exception surface that shows it, the capability that clears it, and the journal rule that keeps the trial balance at zero. None of those appear in the feature's name.

**Worked example:** Owner asks for 'gift-card redemption'. Narrow slice: check balance >= amount, decrement, done — exactly right for the storefront. Run the lens: an offline till burns PKR 2,000 off card X at 13:02 while the website burns PKR 1,500 off the same card at 13:05. Both customers already walked out with goods. On sync the second burn cannot be rejected: it happened. It must post through an unconditional path, take the balance negative within the offline burn cap that bounds the exposure, emit a gift-card variance — the direct analogue of the StockVariance an oversell raises under R5 — onto the brand finance queue, and book to a shrinkage-style contra account so the ledger still balances. InventoryService.move() versus postUnconditional() is the existing shape to copy. A finance queue, a variance entity and an accounting rule are in scope for 'gift-card redemption'; nothing about those three words says so.

**Done test:** The plan contains a table with one row per write the feature makes, each classified REQUEST or RECORD. Every RECORD row names its unconditional entry point, its variance entity, the queue that surfaces it, the permission key that clears it, and its accounting treatment. A write nobody can classify is a write nobody understands, and the plan is not done. A RECORD path reachable through the same method name as the REQUEST path fails, as does a variance nobody is named to clear.

**Breaks without:** One codebase serves a retail till, an SME website and a corporate branch node, and the same service is called by all three — so a refusal that is correct for one silently deletes revenue for another. An offline sale rejected at sync leaves the ledger asserting stock that physically left the building, and that branch's trial balance never balances again. At chain scale nobody sees it per sale; it emerges months later as an unattributable stock-count discrepancy spread across 40 branches and 100+ users, any of whom might have caused it, with no variance row to point at.

### Lens: The switch, its scope, and who may throw it

**Question:** This feature starts corrupting data for one brand at 02:00 on a Saturday. What exactly gets turned off, at which tier — organization, brand, branch, till, role — who may turn it off without a deploy, what does every dependent surface render while it is off, and what happens to work already in flight?

**Why:** 'Add a feature flag' produces nothing. This question produces a runtime settings key with a stated scope tier, a capability that changes it, an audit entry naming actor and reason, a designed off-state for every consumer surface, and an explicit rule for in-flight work. It also forces an honest answer where none exists: the MODULES allowlist is build-time environment configuration, so 'we would drop it from MODULES' means redeploying every node — say that, with the node count and the minutes, or build the runtime switch.

**Worked example:** Owner asks for 'loyalty points'. Narrow slice: accrue on order paid, burn at checkout. Run the lens: a bad accrual rule is minting points at one brand. 'Turn off loyalty' is three switches with three blast radii. Stop accrual — safe and reversible, the balance simply stops growing. Stop burn — customer-facing: the till must state why, and a basket already tendered must still honour the points it quoted thirty seconds ago. Hide the surface — a nav change, plus an off-state for every order-detail panel and customer-account page that renders a points row, and 'blank box' is not an off-state. Each switch is a settings row read at runtime, scoped to the brand, guarded by its own capability rather than a blanket settings grant, audited with actor and reason, and mirrored into the POS policy cache with a stated staleness bound so a till whose uplink is down stops accruing within minutes of head office throwing the switch rather than an hour later. None of that is in the words 'loyalty points', and all of it is loyalty points.

**Done test:** The plan names one switch per independently-failing behaviour, each with: the settings key, the tier it is scoped at, the permission key that changes it, where the change is audited, the rendered off-state of every consumer surface listed by name, the in-flight rule, and the maximum time an offline node may keep acting on a stale copy. A switch with no named permission key fails. A switch whose off-state for any listed surface is an error or a blank fails. 'Redeploy without the module' passes only with the node count and elapsed minutes written down and accepted.

**Breaks without:** One deployment serves one brand but an organization runs several, so a switch scoped a tier too high turns a one-brand incident into an all-brand outage, and a switch that only exists at build time cannot be thrown at all without deploying to 40 branch boxes, some of which are offline. With 100+ roles an unguarded switch is reachable by everyone holding a broad settings capability, while a switch reserved to super admin is unreachable at 02:00 — either way the real mitigation becomes a developer with direct database access, which is precisely the event the audit trail exists to make impossible.

## Domain: Lifecycle reversal and the books

### Lens: The reversal document, not the reversal flag

**Question:** For every forward fact this feature writes — a StockMovement row, a JournalEntry, a CashMovement, a tax line, an allocated document number — what is the NAMED reverse document that undoes it, and can that document be issued for PART of the original, MORE THAN ONCE, until the original is exhausted? Name its entity, its number series, its quantity field, and its foreign key back to the specific original line it reverses.

**Why:** A status enum and a boolean cannot carry a quantity. `OrderStatus.RETURNED` is order-wide; `Payment.refundAmount` is one number on one payment row. Neither can express "2 of 5 shirts came back Tuesday, 1 more on Friday, approved by two different people." The moment a reversal must be partial, a feature built on a flag has exactly two options — lie (reverse the whole thing) or refuse (reverse nothing) — and the first is invisible until an accountant finds it months later. Asking this question before building forces the reverse document into the schema while the schema is still cheap to change.

**Worked example:** This repo already fails it, and the failure is in production code. `PaymentsService.refund()` (apps/api/src/modules/sales/payments/payments.service.ts:289) accepts an optional partial `amount`, stores it in `Payment.refundAmount`, and publishes `PaymentRefunded` carrying that partial amount. `PostingRulesSubscriber.onPaymentRefunded()` (apps/api/src/modules/money/accounting/posting-rules.subscriber.ts:148) ignores `payload.amount` entirely and calls `reverseEntry()` on the FULL `OrderPlaced` entry and the FULL receipt — so a PKR 500 goodwill refund on a PKR 50,000 order erases PKR 50,000 of Sales Revenue, its Tax Payable and its COGS from the ledger. Its own doc comment asserts "nothing sets it to less than the full amount"; `RefundPaymentDto` and `POST /:paymentId/refund` (payments.controller.ts:107, "full or partial") do. Contrast the exemplar the same repo got right: `TransfersService.receive()` (apps/api/src/modules/supply-chain/transfers/transfers.service.ts:166) takes per-line `quantityReceived`, moves only what arrived, bills only what arrived, and writes the shortfall off as its own explicit `WRITE_OFF` StockMovement with a note naming dispatched-vs-received. That is what a quantified partial reversal looks like; `RETURNED` is what a flag looks like.

**Done test:** The reviewer picks one forward write the feature makes and asks to see the database row that records HALF of it being undone, twice, on two dates, by two actors. If the answer is an enum value, a nullable `*At` timestamp, or a single amount column living on the forward row, it fails. Second half of the test: `DocumentPrefixes` in apps/api/src/core/settings/document-prefix.ts gains an entry for the reverse document (it has `invoice`/`INV` and no credit note today), or the plan states in one sentence why this particular reversal needs no number of its own.

**Breaks without:** Partial reversal is the normal case above shop scale — a disputed line on a 40-line corporate invoice, a short-shipped B2B release, a goodwill credit on one garment. With a flag, every one of those either reverses too much (revenue understated by the difference) or gets booked as a hand-typed journal entry. Once reversals live as manual JEs, `ConsolidationService`'s inter-brand elimination has no matched `InterBranchInvoice` pair to net against, so a multi-brand consolidated P&L stops balancing, and Aged Receivables keeps ageing a receivable that was silently voided. At 100+ roles the manual JE is also the audit hole: the reversal has no link back to the order line, so nobody can answer which sale it undid.

### Lens: The undo fan-out

**Question:** Enumerate every side effect the FORWARD path fires — grep its own service for `.create(`, `inventory.move(`, `events.publish(`, every email, every counter, every replicated row — and for each one state which of three it is: reverses automatically (name the method), needs a human (name the screen and the permission), or is deliberately irreversible (one sentence why). A forward side effect with no row in that table is the hole the money falls through.

**Why:** A forward path is written as one transaction and one event fan-out. The reversal path is written months later by someone reading only the service that owns the status field, so coverage is invisible from inside the reversing code — the missing undoer leaves no compile error, no failing test, and no log line. It is discoverable only by enumerating the forward writes first, which is why this is a question asked before building and not a checklist item applied after.

**Worked example:** Cancel/return in this repo covers two of its side effects and silently drops at least four. `OrdersService.changeStatus()` (apps/api/src/modules/sales/orders/orders.service.ts:698) restocks via `inventory.moveMany()` at the sold-from `order.locationId`, and `PostingRulesSubscriber.onPaymentRefunded` reverses the ledger. Not covered: (1) a cash refund at the till writes NO `CashMovement` — `PaymentsService.refund()` never touches the shift — so the drawer is physically short by the refund amount and the Z-report's over/short is wrong with no record of why; (2) `PosShiftsService.recordCashMovement()` (apps/api/src/modules/sales/pos/pos-shifts.service.ts:63) refuses a closed shift, so yesterday's cash sale refunded this morning has nowhere to post at all, not even manually; (3) the `Shipment` row stays `DISPATCHED` with a live courier label on a cancelled order; (4) `Order.reviewRequestSentAt` is untouched, so `MarketingAutomationCron` still emails the customer asking them to review the garment they just returned.

**Done test:** The plan contains a literal table with one row per forward write or published event found in the feature's own code, and every row's third column is filled with a service method name, a screen route plus permission key, or the word "irreversible" plus one sentence of reason. An empty cell fails the review. A reviewer verifies the enumeration is complete by grepping the forward service themselves and matching the count — the table is falsifiable against the code, not against an opinion.

**Breaks without:** At chain scale an uncovered side effect is not a bug report, it is a nightly cash variance in a branch nobody can attribute. Multiply the missing till `CASH_OUT` by 40 branches and 100 cashiers and the over/short report becomes noise — which is precisely where real till theft hides, because every drawer is already short for a legitimate unrecorded reason. In the corporate edition the same class of hole ships a cancelled order via a live courier label and pays sales commission on revenue that was reversed, and because each uncovered effect lives in a different module (pos, orders, marketing, payments), no single team's tests ever see the gap.

### Lens: Who may unmake it, how large, how late, and whose

**Question:** Reversal authority is never the same capability as the forward action. Before building, state: which permission key gates the UNDO, distinct from the DO; what value band each role may reverse; how many hours or days after the original the undo stays self-service; whether a user may reverse their own original; and what the code does when the `FiscalPeriod`, `PosShift`, or node-sync boundary the original belongs to is already closed.

**Why:** In a one-shop deployment the honest answer is "the owner does it," so the question never gets asked and the reversal inherits whatever permission the forward route already had. In a 100-role corporate deployment the cashier, shift supervisor, branch manager, regional controller, finance approver and auditor all sit on that single action with six different ceilings. The closed-period half has exactly one correct answer per business — reroute with a link back, or refuse — and it must be chosen deliberately, because both stances already exist in this codebase and disagree.

**Worked example:** `@RequirePermission('orders.manage')` is declared once at class level on the admin orders controller (apps/api/src/modules/sales/orders/orders.controller.ts:87), so the same key that lets a junior edit `staffNote` lets them push a DELIVERED order to RETURNED — restocking stock and triggering the ledger reversal above. `payments.approve`, the key for confirming a bank transfer arrived, is the same key that refunds it (payments.controller.ts:87 covers both :paymentId/approve and :paymentId/refund). On the closed-period half the product contradicts itself: `AccountingService.reverseEntry()` (apps/api/src/modules/money/accounting/accounting.service.ts:102) dates the reversal `now` and calls `resolveOpenPeriod(now)`, so a refund of a December sale lands in March with no marker tying it to a closed year, while `PosShiftsService.recordCashMovement()` throws `This shift is already closed` for the analogous case. Two opposite answers to one question inside one deployment.

**Done test:** The feature adds at least one permission key naming the undo — `orders.cancel`, `payments.refund`, `pos.void` — registered in `PERMISSION_CATALOG` in packages/shared AND granted in `ROLE_PERMISSION_SEED` (packages/shared/src/permissions.ts:360), not merely inserted as a `Permission` row. A reversal route that inherits its forward controller's class-level `@RequirePermission` fails. And the reversal code path contains an explicit branch on the closed period/shift/node — a named exception or a documented reroute that records which closed period the original belonged to. Reaching `resolveOpenPeriod()` with no stated intent about the original's period fails.

**Breaks without:** Roles can be created by the hundred and they all collapse onto the same three coarse keys, so every corporate deployment hits the identical UAT blocker — "a store clerk can refund PKR 2,000,000" — and the fix under deadline is a per-client tweak to the guard, which is exactly the branch-per-client failure the sector/brand/branch axes exist to prevent. The second break is audit: with no closed-period stance, a December reversal silently rewrites a FiscalYear that was already closed and signed off, so last year's revenue figure is not reproducible, and an audited corporate client cannot sign the current year either. Neither failure is visible in the retail edition, which is why it ships.

## Domain: Concurrency, volume and performance

### Lens: The second copy of the write

**Question:** Name the two moments this write arrives twice — the retried HTTP call, the double-tapped button on a branch tablet, the redelivered outbox event, the replayed offline POS sale, the webhook a delivery partner sends again — and name the column, with its unique constraint, that makes the second arrival a no-op instead of a second fact. Then name what the loser of a simultaneous write sees on screen. If you cannot name the column, the feature is not designed yet.

**Why:** Duplicates are this system's design, not its failure mode. `OutboxDispatcher` claims with `FOR UPDATE SKIP LOCKED` and retries to `MAX_ATTEMPTS = 8`, so delivery is at-least-once by construction; RETAIL-ERP R5 says a sale that already happened is never rejected by sync, which means the till replays whatever it buffered offline. A handler that is merely 'usually called once' will double-post. The read-then-write shape is the same defect wearing a second face: two actors both read the old value and both write, and the second silently erases the first with no error anywhere.

**Worked example:** WO-22's 'receive a transfer' looks like one write. It is six: decrement at the dispatching branch, close the in-transit row, increment at the receiving branch, a `StockMovement` per line, an inter-branch `JournalEntry`, and `posting-rules.subscriber` firing off the domain event — and that subscriber is fed by the at-least-once outbox, so it gets redelivered whether or not the HTTP call repeats. Receive it twice and stock increments twice, the journal double-posts, and the trial balance stops balancing. What the lens pulls into scope alongside 'receive': a client-supplied idempotency key persisted under a unique constraint; the subscriber keyed on (eventId, handler) so redelivery is a no-op; the status transition expressed as a guarded `updateMany({ where: { id, status: 'IN_TRANSIT' } })` whose `count === 0` branch renders 'already received by Ali at 14:02', not a 500 — the `InventoryService.move()` predicate-on-write idiom applied to a state column instead of a quantity. Second instance, and the one that bites at 100+ roles: `roles.service.ts` rewrites a role's grants as `deleteMany({ where: { roleId } })` then `createMany`, on `this.prisma` rather than inside a transaction. Two admins saving the same 400-checkbox role a second apart is last-writer-wins with no version column and no record of whose set survived — and because `JwtStrategy` re-resolves permissions from the database on every request, any user holding that role who lands inside the delete/create window gets a 403 mid-checkout from a role that momentarily has no grants at all.

**Done test:** Two tests per write path, both asserting exact row counts rather than 'no error': the endpoint called twice with the same idempotency key, and the event handler dispatched twice with the same event id, each proving one `StockMovement` per line, one `JournalEntry`, one document number. Plus: grep the diff for a `findUnique`/`findFirst` on a row followed by an `update` of that same row's state or quantity — the count must be zero, or each survivor named in the PR with why it is safe. Every state transition in the diff is a guarded `updateMany` whose `count === 0` path produces a specific message naming who won; a transition that can only succeed fails the lens.

**Breaks without:** At 40 branches with offline-capable tills, a duplicate is a Tuesday, not an incident. Stock quantity drifts from physical count, the trial balance stops balancing, and two invoices carry `INV-2026-0041`. None of it surfaces at the moment of damage — it surfaces at month-end close, weeks of movements later, and the duplicate rows are byte-for-byte indistinguishable from real ones, so there is nothing to reconcile against and no way to unwind it. With 100+ users across three editions, the audit trail names 40 possible actors and settles nothing. The role-grant race is worse than a wrong number: a permission silently disappears, the affected user is told 'you don't have access', and the admin who saved second sees the role exactly as they intended it.

### Lens: The hundred-thousandth row

**Question:** State the row count this feature's largest table reaches at the corporate edition — orders, `StockMovement`, `Party`, `RoleGrant` — and the number of SQL statements one page of it issues at that size, and how many of those statements the database can serve from an index. If either number is unknown, the screen was designed against seed data and its behaviour at the third edition is a guess.

**Why:** One build ships to a corner shop, an SME and a 40-branch chain; there is no enterprise fork in which to fix this later, and the corporate client opens the screen on day one. And the damage is not that the page feels slow: an unbounded query holds a connection from a fixed-size pool on a single-process node, so one manager's report page starves every till in every branch that node serves. A query whose cost grows with the tenant is a time bomb with the fuse length set by the client's success.

**Worked example:** Two shapes, both already in this repo. `purchasing.service.ts` numbers a PO by taking `pg_advisory_xact_lock` for the year and then running `MAX(CAST(split_part("number", '-', -1) AS INTEGER))` over every `PurchaseOrder` matching the year's prefix — correct, and invisible at 300 POs a year. At 100k GRNs a year across 40 branches it serialises every goods receipt in the chain behind a scan that grows all year, while the same feature's `TransferNumberCounter` upsert next door is O(1) and needs no lock at all. Second shape, the admin orders list: 300k orders, each row rendering customer name, branch, payment status and a permission-gated action. Written naively that is one query plus four per row, the pager's `count(*)` scans the whole table on every keystroke of the search box, and because permissions resolve fresh from the database on every request, a user holding 12 of the 120 roles pays that role-to-grant expansion once per row instead of once per request. What the lens pulls into scope: keyset pagination rather than offset (page 4,000 of an offset pager reads 100,000 rows to discard 99,975), a bounded default date window, the composite index that actually serves the WHERE plus ORDER BY pair, one batched include, a debounced search, and one resolved permission set per request.

**Done test:** A seed script that loads the feature's largest table to 100k rows exists in the repo and is named in the PR, and the PR quotes three measured numbers from running against it: wall-clock for the default view, SQL statement count for one page, and `EXPLAIN ANALYZE` output showing an index scan rather than a Seq Scan — for the default view and for the deepest page a user can actually reach. Any statement the feature sends with no LIMIT fails outright. Any per-row query inside a loop over the result set fails outright. 'Looks fast locally' against the dev seed is not evidence and does not count.

**Breaks without:** The three editions share one codebase, so the failure does not arrive as a slow screen at a client who could tolerate it — it arrives as the corporate tenant's stock report holding six database connections for ninety seconds while the tills on that node queue behind an exhausted pool, at 6pm on a sale day. Nobody connects the two: the report eventually renders, the cashiers see a 500 with no cause, and the bug is filed against POS. At 100+ users the multiplier is not the row count alone but the concurrent readers of it, and the per-row permission expansion means the biggest, most privileged, most valuable tenant — most roles, most branches, most rows — is precisely the one the screen is slowest for.

### Lens: The busiest minute, and the lock you hold through it

**Question:** What is the largest single invocation this feature will ever receive — the fullest stock count, the widest price update, the year-end import, one minute of a sale day — and, at that size, how many row locks does it hold, for how many seconds, inside how many transactions, and how many outbox rows does it enqueue? Then name the POS action that blocks while it runs.

**Why:** This repo's outbox drains `BATCH_SIZE = 25` every `POLL_INTERVAL_MS = 2_000`, ordered by `createdAt` — a hard ceiling of 750 events a minute, strictly FIFO. Anything that enqueues more than that does not just slow itself down; it pushes every unrelated event in the system behind it. And a bulk write inside one transaction holds exactly the row locks the tills need, at exactly the hour the bulk job was scheduled to avoid.

**Worked example:** A stock count posted at an 8,000-variant branch. Each line runs `InventoryService.move()`: a guarded `updateMany` on `VariantLocationStock`, a raw `UPDATE` recomputing `ProductVariant.stock`, a `StockMovement` row, and a domain event. As one transaction that is roughly 16,000 row locks held for the job's whole duration, and every concurrent sale of any of those variants waits on it — `move()` already carries a comment about lock ordering to avoid deadlocks, so a second bulk path that acquires them in a different order does not slow the till down, it deadlocks against it and surfaces as a random 500 at the register. Meanwhile the 8,000 outbox rows drain at 25 every 2 seconds: about eleven minutes, FIFO, so the customer who ordered at 18:03 gets their confirmation email at 18:14 and `posting-rules.subscriber` writes that evening's journals late. What the lens pulls into scope: a chunk size with a stated reason and a transaction boundary per chunk, resume-from-line (a count that dies at line 6,000 must not restart from zero and must not have posted half of itself), lock acquisition in the same order `move()` documents, and a stated answer for a 50,000-deep outbox — which lane drains first, and what a poison event hitting `MAX_ATTEMPTS = 8` does to everything queued behind it.

**Done test:** The PR states the worst-case N and the rows-per-transaction boundary as numbers, and a test runs the feature at that N — or at a scaled N with the arithmetic shown — while a concurrent single POS sale of a variant *inside* the batch completes within a stated bound and raises no deadlock. The PR also quotes outbox depth immediately after the run and the drain time implied by 25 events per 2 seconds. An answer of 'we'll monitor it' or an unstated transaction boundary fails; so does a bulk path with no resume, because 'run it again' is not a recovery story once half the rows have posted.

**Breaks without:** Locks held across a bulk job do not degrade throughput, they stop the shop. A till that cannot complete a sale because head office started a seasonal price update is a business outage caused by an admin screen, and the cashier sees an error bearing no relation to its cause, in a branch whose staff cannot see the job that caused it. At corporate scale the bulk paths are not rare events to be scheduled around: nightly supplier imports, monthly stock counts across 40 branches, price updates spanning every variant, and a hundred-plus users each able to launch one from a screen that gave no hint of its cost. Without the chunk, resume and lane answers, each of those is a scheduled outage the roster does not know about, and the outbox backlog means the visible symptom is not the import at all — it is order confirmation emails arriving eleven minutes late and journals posting to the wrong evening.
