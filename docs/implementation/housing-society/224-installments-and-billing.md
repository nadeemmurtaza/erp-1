# 224 — Installments and billing

> **Industry-specific module.** This belongs to the **housing-society sector pack** (real estate / society management), not to `core`. It is enabled only in housing-society deployments through the `MODULES` allowlist; other sectors never load it, and core never imports it.
>
> **Status: Planned.** Module: `society-billing`. One job: **know what each
> member owes, and when.** Reuses `receivables` (dunning, statements, credit
> notes) and takes doc 151 (layby installment sales) as the precedent for a
> staged schedule.

## 1. Payment plan

`PaymentPlan` is a **versioned** template; a booking stores
`paymentPlanVersionId`. Editing a plan creates a new version and never
touches installments already generated.

| Part | Examples |
|---|---|
| Down payment / booking amount | % or fixed |
| Installment cadence | monthly, quarterly, half-yearly |
| Count and amounts | equal, or custom per-line |
| **Milestone lines** | on allotment, on development progress, on possession |
| Balloon/lump sum | at a named date |
| Discount | lump-sum discount for full prepayment (rule, versioned) |

## 2. Installment

`Installment`: `bookingId`, `seq`, `kind` (`DOWN` `REGULAR` `MILESTONE` `BALLOON`
`SOCIETY_CHARGE`), `dueDate`, `amountMinor`, `paidMinor`, `status` (`SCHEDULED` `DUE`
`PARTIAL` `PAID` `OVERDUE` `VOID`), `planVersionId`. Generated by a pure function
`schedule(plan, booking) → Installment[]` (dry-run safe; no write inside it).
`paidMinor` is **never edited directly** — it is the sum of
`ReceiptAllocation` rows (doc 225), recomputed/checked, so the schedule and
the receipts cannot disagree.

## 3. Late fees and surcharges

`LateFeeRule` (versioned, per project): grace days, method (`FLAT` | `PERCENT_PER_PERIOD` | `DAILY`), cap, compounding (off by default).

| Parameter | Default value | Why | Enforced | Degrades |
|---|---|---|---|---|
| Grace period | 10 days after due date | Matches a typical bank-transfer clearing window; shorter would charge members for the society's own posting delay | `computeLateFees` | Rule missing → no fee, an alert to admin |
| Late fee | 2% of the overdue amount per month, simple (not compound), prorated daily | Common and defensible rate; compounding is opt-in because it surprises members | same | — |
| Cap | 25% of the original installment | Stops a long-dormant account from ballooning past what a court/regulator would accept | same | Cap hit → flagged for manager |
| Run schedule | nightly at 02:00 society time | Off-hours; idempotent by `(installmentId, asOfDate)` | cron | Missed night re-runs safely next night |

These are **defaults in `Setting`**, edited per project by
`society.billing.rules` with a second signature and an audit row holding the
old and new rule; a society's own law or bylaws override them. The numbers
above are proposals to confirm, not facts about any client.

* **Late-fee run is a dry-run-first function**: `computeLateFees(rule, installments, asOf)` returns a preview; staff can
  see exactly what would post for last month before it does.
* **Waiver** of a late fee is an approval (doc 223 §7), never an edit.
* Late fees are separate `Installment(kind=SOCIETY_CHARGE)` lines stamped with
  `lateFeeRuleVersionId`.

## 4. Society charges

`SocietyCharge` definitions: development, possession, transfer fee, NOC fee,
corner/park premium, membership, documentation, maintenance (roadmap, doc
230). Each has an amount rule, an account mapping (doc 226), tax treatment
(via the existing `tax` module, off by default), and applies at a named event
(`on_booking`, `on_transfer`, `on_possession`).

## 5. Statements and follow-up

* **Member statement**: booking price, schedule, paid, due, overdue, late
  fees, receipts — from the existing `receivables` statement path, filtered by
  booking. Printable and downloadable by the member in the portal.
* **Dues list / aging** (30/60/90+) with drill to exact installments.
* **Reminders**: `receivables` dunning is reused; audience resolves from
  `society.billing.follow_up` + project scope (never a literal address). Zero
  holders → admin escalation; large lists → a digest.
* **Post-dated cheques** are held as instruments (doc 225), shown against
  the installment they will clear, never counted as paid until cleared.

## 6. Authority

Plan edits and late-fee rule edits affect **future** installments only and
need a second signature. Manual adjustment of an installment is a
`BookingTransaction`-style adjustment row with a reason, not an edit; a
credit/debit note is the document.

## 7. Acceptance criteria

1. `schedule()` for a 36-installment plan produces rows summing exactly to the booking price, to the paisa.
2. Editing a plan after generation changes no existing installment.
3. `computeLateFees` in preview writes nothing; running the nightly job twice posts each fee once.
4. `Installment.paidMinor` always equals the sum of its allocations (invariant test).
5. A dues-aging report's buckets sum to total overdue, each cell drills to rows.

## 8. Permissions

`society.billing.view`, `society.billing.rules`, `society.billing.adjust`,
`society.billing.waive`, `society.billing.follow_up`.
