DOMAIN EVENTS. Catalogue: `apps/api/src/core/events/domain-events.ts` — `export const DomainEvent = {...}` with ~40 names (order.placed, payment.succeeded, catalog.product_reorder_point_reached, inventory.stock_replenished, transfers.inter_branch_invoiced, production.work_order_*, identity_verification.*). Publishing: `EventBusService.publish(name, payload, tx = this.prisma)` in `events/event-bus.service.ts` writes one `outboxEvent` row; the `tx` parameter is how the event commits in the same transaction as the state change. Delivery: `EventBusService.dispatch()` calls `EventEmitter2.emitAsync` — in-process only. Subscribers use `@OnDomainEvent(...)` (`events/on-domain-event.decorator.ts`), which wraps `OnEvent(event, { async: true, promisify: true })`. `EventsModule` is `@Global`, `maxListeners: 50`, `ignoreErrors: false`.

OUTBOX. `events/outbox.dispatcher.ts`: `@Interval(2000)` drain, `BATCH_SIZE = 25`, `MAX_ATTEMPTS = 8`, claim via raw `SELECT "id" FROM "OutboxEvent" WHERE status='PENDING' AND "availableAt" <= NOW() ORDER BY "createdAt" ASC LIMIT 25 FOR UPDATE SKIP LOCKED`, then `updateMany` to PROCESSING. Guarantees: atomicity with the producing transaction; multi-instance safety via SKIP LOCKED; at-least-once delivery (handlers must be idempotent — stated in the decorator doc). Does NOT guarantee: ordering across handlers (all handlers of one event are fanned out by emitAsync; one throwing retries the whole event, so already-succeeded handlers re-run); cross-process delivery (no broker); exactly-once; anything after 8 attempts — status becomes `FAILED` and nothing retries or alerts except the readiness probe's count. Backoff `min(2^n * 1000, 300_000)`. Model `OutboxEvent` (`apps/api/prisma/schema/core.prisma:361`) has no tenant/node/brand column and no partition key.

EXTENSION POINTS. `core/extension-points/` plus `core/checkout/checkout-validator.registry.ts`, all provided by `ExtensionPointsModule` (`@Global`). Four: `EntityEnrichmentRegistry` (named point, e.g. "orderItem.stitchingJob"; `register()` throws on a second registration for one point; `enrich()` returns an empty Map when nobody registered), `CheckoutValidatorRegistry`, `CartLineValidatorRegistry` (measurements registers 'measurements', stitching registers 'stitchingOptions'), `StockIntakeRegistry` (`register()` from inventory's `onModuleInit()`; `recordIntake()` no-ops when inventory is off; explicitly NOT for same-transaction writes). ## Where a narrow build goes wrong here

- Settings are a single global key/value table with a 30s per-process cache and no brand, branch, location, department or role scope — any feature that assumes per-location or per-department configuration has no place to store it, and a write on one API instance is invisible to others for up to 30 seconds.
- The outbox is a single unpartitioned table drained every 2s in batches of 25 by every instance; at 100+ locations and 10k+ products the event volume per drain and the fan-out to in-process EventEmitter2 handlers (maxListeners 50) are the ceiling, and a permanently FAILED event is surfaced only as a count on /health/ready.
- Delivery is in-process only: a subscriber must live in the same Node process as the dispatcher, so no module can be scaled or deployed independently despite the independence rule.
- Enabling a module is process-global via the MODULES env var, read before DI — one brand or location cannot have a module that another lacks without a separate deployment.
- There is no rank model and no department model; role is a flat Role table with no hierarchy, no parent role, no inheritance and no rank ordering, and USER_ROLES is still a four-value enum. Anything assuming 100+ ranks or an org chart has to invent the model.
- AdminScope exists in code (scope.guard.ts) but the organization module is off by default and, per the file's own comment, every deployment today resolves with zero scope rows — a feature relying on brand/branch scoping is effectively unscoped in practice.
- Audit is opt-in per call site (24 of 26 modules touched, and only some methods within them), records a free-text action/entity pair with no schema and no diff, and swallows its own failures — it cannot be relied on for compliance-grade trails.
- Enrichment points take exactly one implementation (register() throws on a second), so two packs cannot both contribute to one core response field.
- KNOWN_MODULE_COUPLINGS has grown to 10 entries, all justified as same-transaction writes; any new feature needing a synchronous cross-module write must either add an eleventh or accept eventual consistency, and the extension-point registries explicitly do not run inside the caller's transaction.
